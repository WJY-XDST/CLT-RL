## 一 先看清机器人和控制方式

### 1.1 机构仍是闭链五连杆

当前机器人每侧有两个主动腿关节、若干受闭链约束的被动关节和一个轮关节。左右两侧合起来，策略控制六个动作，但机器人 Articulation 中的关节总数不止六个。

需要先分开三个数量：

| 数量 | 当前含义 |
| --- | --- |
| 四个主动腿关节 | `LB_joint`、`LL_joint`、`RB_joint`、`RL_joint` |
| 两个轮关节 | `LW_joint`、`RW_joint` |
| 六维策略动作 | 按左腿、左轮、右腿、右轮穿插排列 |

不能把“动作有六维”理解为模型只含六个关节。被动关节虽然没有对应 Actor 输出，仍会参与质量、惯量、碰撞和闭链约束求解。

### 1.2 当前腿部直接输出关节角目标

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 262 至 275 行。

```python
wheel_damping: float = 0.5
wheel_control_mode: str = 'implicit_velocity'
leg_control_mode: str = 'implicit_joint_position'
leg_joint_stiffness: float = 300.0
leg_joint_damping: float = 3.0
# Direct-joint mode: normalized columns 0/1/3/4 map to LB/LL/RB/RL.
leg_joint_position_offset: tuple[float, float, float, float] = DEFAULT_JOINT_OFFSETS
# Zero action and the actual reset pose agree, including passive loop joints.
# Historical checkpoints explicitly retain cad_zero_v0 during replay.
joint_reset_profile: str = NOMINAL_JOINT_RESET
leg_joint_position_scale: tuple[float, float, float, float] = (0.3, 0.3, 0.3, 0.3)
leg_joint_target_limit_margin = 0.01  # [rad] inside articulation hard stops
# Direct motor-position mode: optional J^T [gravity force, 0] only.
leg_joint_gravity_feedforward = True
```

`leg_control_mode` 是执行分支的开关。当前默认值是 `implicit_joint_position`。在这种模式下，Actor 的四个腿部输出被解释为四个主动关节的归一化位置动作。

`leg_joint_stiffness` 和 `leg_joint_damping` 是关节驱动的 PD 参数。它们不是 PPO 的学习率，也不是神经网络的参数。策略在训练中学习目标角，PhysX 在物理步进中根据目标与实际状态计算关节驱动作用。

`leg_joint_position_scale=(0.3,...)` 表示一个归一化动作单位对应 0.3 rad 的目标角变化。它不表示电机最大允许转角就是 0.3 rad。实际目标还要与 Articulation 的关节限位取交集。

`leg_joint_gravity_feedforward=True` 表示启用独立重力前馈。它不把高度误差转换成第二套腿长反馈，也不在目标角上偷偷增加一个 IK 修正量。

两条并行路径如下：

```text
Actor 的四个腿部动作
    → leg_control.py 的 joint_position_targets()
    → 四个主动电机关节目标角
    → Articulation.set_joint_position_target()
    → PhysX 隐式关节位置驱动

实际关节角和速度
    → five_bar_state() 得到虚拟腿状态与 Jacobian
    → gravity_feedforward() 得到径向补偿力
    → five_bar_torques() 得到四个关节前馈力矩
    → Articulation.set_joint_effort_target()
```

所以，文件名中的 `vmc` 不能代替执行分支分析。当前直接关节模式仍使用五连杆正运动学和 Jacobian，但不使用虚拟腿长 PD 或 IK 生成策略目标角。

### 1.3 两个轮动作的含义不同

轮子的两维动作先乘 `action_scale_vel=15`，得到前进为正的目标轮速，单位为 rad/s。随后环境在写入边界处理右轮镜像坐标，再调用 `set_joint_velocity_target()`。

```text
Actor 的第 2 和第 5 列
    → 轮动作限幅
    → 乘以 15 rad/s
    → 左右轮坐标符号转换
    → PhysX 速度驱动
```

这里的第 2、5 列采用 Python 从零开始的下标。它们是六维向量中的第三、第六个数。

## 三 从配置文件的导入开始

### 3.1 Isaac Lab 导入提供哪些能力

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 8 至 16 行。

```python
from isaaclab.actuators import ImplicitActuatorCfg
import isaaclab.sim as sim_utils
from isaaclab.assets import ArticulationCfg
from isaaclab.envs import DirectRLEnvCfg, ViewerCfg
from isaaclab.scene import InteractiveSceneCfg
from isaaclab.sensors import ContactSensorCfg
from isaaclab.sim import SimulationCfg
from isaaclab.terrains import TerrainImporterCfg
from isaaclab.utils import configclass
```

这些名称大部分以 `Cfg` 结尾，表示“配置”，不是当前仿真中的对象实例。

`DirectRLEnvCfg` 是直接强化学习环境的配置基类。`WheelLeggedVMCFlatEnvCfg` 继承它，补上这辆轮腿机器人的字段。对应的执行类则继承 `DirectRLEnv`。

`ArticulationCfg` 描述机器人的 USD 路径、初始状态和执行器分组。真正创建并管理机器人的是 `Articulation`。因此下面两句处于不同阶段：

```python
# 教学示例：配置对象和运行对象的区别。
robot_cfg = ArticulationCfg(prim_path="/World/envs/env_.*/Robot")
robot = Articulation(robot_cfg)
```

第一句只构造配置，第二句才构造运行对象。实际工程中第一步在配置文件，第二步在环境 `_setup_scene()`。

`ImplicitActuatorCfg` 配置由 PhysX 求解器处理的隐式位置或速度驱动。它不表示神经网络，更不表示自动寻找最优 PD 参数。

`ContactSensorCfg` 描述接触传感器的读取对象和更新节奏。`InteractiveSceneCfg` 描述批量环境的数量与间距。`TerrainImporterCfg` 描述地形。`SimulationCfg` 描述物理步长、物理材质与底层仿真参数。

### 3.2 configclass 为什么允许这样写字段

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 183 至 204 行。

```python
@configclass
class WheelLeggedVMCFlatEnvCfg(DirectRLEnvCfg):
    """唯一环境配置：新车数据、执行器、观测、奖励、命令与物理设置。

    默认直接关节目标角加隐式 PD；explicit_vmc 模式保留在同一环境中。
    不继承旧车配置，不在 mine_env_cfg 或 reward profile 中二次覆写。
    """

    # -- env --
    episode_length_s = 20.0
    decimation = 4
    action_space = 6
    observation_space = 27
    state_space = 0
    leg_model: str = 'mine_five_bar'
    leg_joint_names: list[str] = MODEL['leg_joint_names']
    wheel_joint_names: list[str] = MODEL['wheel_joint_names']
    leg_body_names: list[str] = [s + n + '_link' for s in ('L', 'R') for n in ('B', 'S', 'L', 'L1', 'L2', 'L3')]
    penalised_body_pattern: str = '(base_link|[LR](B|S|L[123]?)_link)'
    five_bar_geometry: dict = MAPPED_FIVE_BAR
    leg_effort_limit: float = LEG_EFFORT_LIMIT
    wheel_effort_limit: float = WHEEL_EFFORT_LIMIT
```

`@configclass` 扩展了配置类的字段处理，并提供 `to_dict()`、复制、替换等能力。配置对象可以再转成普通字典，供 Hydra 和 RSL-RL 使用。

`leg_joint_names: list[str] = MODEL[...]` 同时包含类型注解和字段默认值。`list[str]` 说明希望保存字符串列表；真正的数据来自 `MODEL`。Python 的类型注解本身不会校验“这四个名字是否与 USD 一致”，项目另外写了契约校验。

这里的 `MODEL`、`MAPPED_FIVE_BAR`、`LEG_EFFORT_LIMIT` 都不是本文件内计算出来的。下面沿导入进入它们的来源。

### 3.3 `configclass()` 在配置准备步骤中的作用

接口源码：[configclass.py:31](../../../IsaacLab/source/isaaclab/isaaclab/utils/configclass.py#L31)。

<!-- api-contract: configclass -->

| 项目 | 说明 |
| --- | --- |
| 作用 | 把项目声明的配置类转换为 Isaac Lab 可使用的配置类型。 |
| 输入 | 被装饰的配置类，例如 WheelLeggedVMCFlatEnvCfg。 |
| 输出 | 处理后的配置类；实例支持字段访问、to_dict、copy、replace、validate 等接口。 |
| 本步骤中的状态变化 | 发生在导入与类定义阶段；当前步骤要继续关注配置字段怎样交给环境，而不是装饰器怎样生成这些方法。 |

回到项目配置类：`decimation`、`action_space`、机器人资产和命令范围都是随后构造环境所需的输入。类型注解说明字段预期类型，车型、几何和控制约定仍由项目的初始化检查确认。

### 3.4 嵌套配置为什么写成 `ObsScalesCfg()`，而不是直接写类名

`obs_scales: ObsScalesCfg = ObsScalesCfg()` 中，冒号后的名字说明字段类型，等号右侧的括号表示创建实例。此时实例保存 `lin_vel` 等参数，稍后环境可以读取 `cfg.obs_scales.lin_vel`。

若误写成 `obs_scales = ObsScalesCfg`，右侧是类对象，运行含义和序列化方式都会不同。若把 `ContactSensorCfg` 当成运行中的传感器，同样会混淆“描述需要什么”和“已经创建了什么”。

教学示例：下面演示嵌套字段的访问，不启动仿真。

```python
cfg_a = WheelLeggedVMCFlatEnvCfg()
cfg_b = cfg_a.copy()
cfg_b.commands.training_motion_scale = 0.25
# cfg_a 仍用于原配置；cfg_b 是准备使用的修改版本。
```

这里选择 `copy()`，是为了让一次实验的修改有清楚边界。直接 `cfg_b = cfg_a` 只给同一个对象增加一个名字，修改 `cfg_b.commands` 也会改到 `cfg_a.commands`。

配置对象不是训练状态快照。复制它不会复制 Actor 参数、Adam 动量、机器人当前姿态或随机数生成器；这些分别属于检查点和运行状态。

### 3.5 `validate()`、类型注解和车型契约各自能检查到哪里

本机 `configclass.py` 的 `_validate()` 从第 244 行开始，递归进入列表、元组、字典和对象成员，寻找 `MISSING` 字段；顶层把缺失路径合成异常。这个校验关注“必填值是否仍缺失”。

它不把所有类型注解变成完整的运行时物理校验。例如给 `wheel_radius` 填一个负数，只要不是 `MISSING`，就不能指望该方法自动证明它合理；`float('nan')` 也需要专门的有限数检查。

本项目因此还调用 `validate_robot_contract()`、动作尺度校验、力矩参数校验和物理开关校验。它们分别检查车型、数组长度与正数条件、执行参数和求解器约定。理解这一分工，才能知道一个错误应在哪里被发现。

配置能成功转成字典，只证明数据表达可用；配置对象通过缺失字段校验，也不代表模型质量、闭链装配和接触动力学已经经过实测。

## 四 穿插阅读 robot_model 文件

### 4.1 模型目录怎样定位

源码：[robot_model.py](../../wheel_legged_gym_isaaclab/robot_model.py)，第 25 至 27 行。

```python
ASSETS = Path(__file__).resolve().parents[1] / "assets/robots/mine"
MANIFEST = json.loads((ASSETS / "manifest.json").read_text())
MODEL = json.loads((ASSETS / MANIFEST["metadata"]).read_text())
```

`Path(__file__)` 表示当前 `robot_model.py` 的文件路径。`.resolve()` 形成绝对路径；`.parents[1]` 回到包含 `assets` 的项目子目录。随后拼上 `assets/robots/mine`。

`/` 在 `Path` 对象中是路径拼接运算，不是数值除法。`ASSETS / "manifest.json"` 得到的是一个文件路径。

`.read_text()` 读取 JSON 文本，`json.loads()` 把文本转换成 Python 字典。于是后面的 `MANIFEST["metadata"]` 是字典索引，得到模型元数据的相对路径。

完整链路是：

```text
robot_model.py 的文件位置
    → ASSETS 资源目录
    → manifest.json
    → metadata 指定的 model.json
    → MODEL 字典
    → 环境配置中的关节名、几何、轮距等字段
```

### 4.2 manifest 选择资产和元数据

当前默认清单见 [manifest.json](../../assets/robots/mine/manifest.json)。与阅读有关的字段如下：

```json
{
  "usd": "export_20261003_181515/mine_closed_chain.usd",
  "training_usd": "export_20261003_181515/mine_closed_chain_training_measured_volume_mass_20261014.usda",
  "metadata": "export_20261003_181515/model.json"
}
```

这是清单节选。`usd` 是基础模型，`training_usd` 是默认训练资产入口，`metadata` 是 Python 读取的模型描述。三者不是相互替代的关系。

实际实验可以在配置中指定另一份配套资产，例如经过解析轮胎碰撞校准的资产。因此“当前默认清单指向什么”和“某个已训练检查点实际使用什么”需要分别看 `manifest.json` 与检查点目录下的 `params/env.yaml`。

### 4.3 MODEL 中最重要的数据

| 字段 | 数据含义 | 当前读取示例 |
| --- | --- | --- |
| `leg_joint_names` | 四个主动腿关节及顺序 | LB、LL、RB、RL |
| `wheel_joint_names` | 两个轮关节及顺序 | LW、RW |
| `wheel_radius` | 轮半径 | 0.06 m |
| `wheel_track_width` | 几何轮距 | 0.4199 m |
| `hip_z` | 髋部几何偏置 | 0.02465354469 m |
| `five_bar` | 原始五连杆几何与映射 | 杆长、零位、倍率、分支 |

关节顺序会影响后面的张量选择。即使四个名字都正确，把左右腿互换仍会让动作发到错误的电机。

`MODEL` 也保留原始 CAD 导出的历史质量汇总，例如 `mass_kg` 和 `supported_mass_kg`。它们不会自动变成当前仿真的总质量。当前刚体质量来自组合后的 USD；重力前馈的名义整车质量来自硬件参数约定。

因此，修改 JSON 中的旧质量数字，不能据此断言已经修改了 PhysX 中每个刚体的质量和惯量。

### 4.4 五连杆为什么还要映射一次

源码：[robot_model.py](../../wheel_legged_gym_isaaclab/robot_model.py)，第 32 至 53 行。

```python

def mapped_five_bar_geometry(geometry):
    """Equivalent wheel-end links in metres; offsets stay at CAD motor zero."""
    result = copy.deepcopy(geometry)
    scale = float(result["scale"])
    if not math.isfinite(scale) or scale <= 0:
        raise ValueError("Five-bar mapping scale must be positive and finite")
    for name in ("upper", "lower"):
        if len(result[name]) != 2:
            raise ValueError(f"Five-bar {name} must contain two link lengths")
        result[name] = [float(value) * scale for value in result[name]]
        if any(not math.isfinite(value) or value <= 0 for value in result[name]):
            raise ValueError("Mapped link lengths must be positive and finite")
    if len(result["offsets"]) != 2 or not all(math.isfinite(v) for v in result["offsets"]):
        raise ValueError("Five-bar requires two finite CAD zero offsets")
    if result["branch"] != 1:
        raise ValueError("This vehicle's CAD five-bar assembly requires branch 1")
    result["scale"] = 1.0
    return result


MAPPED_FIVE_BAR = mapped_five_bar_geometry(MODEL["five_bar"])
```

先看 `copy.deepcopy(geometry)`。输入是一个含列表的字典，如果只复制外层，内层列表仍可能共用；深拷贝避免后续修改污染原始 `MODEL["five_bar"]`。

`scale = float(result["scale"])` 取出等效映射倍率。原始上杆约 0.0945 m、下杆约 0.1125 m，倍率约 2.222222。乘完后，运行时使用的等效上杆约 0.21 m、下杆约 0.25 m。

循环中的 `for name in ("upper", "lower")` 分别处理两组杆长。每组要求正好有两根杆，且所有长度必须有限、为正。这样可以在创建仿真前发现损坏的几何数据。

`offsets` 是 CAD 电机零位到运动学角度的偏置，`branch` 是闭链装配分支。它们都参与正运动学，但与 Actor 动作映射的 `leg_joint_position_offset` 不是一回事。

最后把 `scale` 写成 1.0，是因为倍率已乘进杆长。若把 0.21 m、0.25 m 再乘原来的倍率，就会把末端位置重复放大。

跨文件传递如下：

```text
MODEL["five_bar"]
    → mapped_five_bar_geometry()
    → MAPPED_FIVE_BAR
    → cfg.five_bar_geometry
    → env._update_forward_kinematics()
    → five_bar_state(q_b, q_l, **geometry)
```

`**geometry` 是关键字参数展开。例如字典中存在 `upper`、`lower`、`offsets`，调用时就相当于分别传入同名参数。

### 4.5 validate_robot_contract 检查什么

源码：[robot_model.py](../../wheel_legged_gym_isaaclab/robot_model.py)，第 56 至 81 行。

```python
def validate_robot_contract(cfg):
    """Fail closed instead of interpreting another vehicle as this one."""
    if cfg.get("leg_model") != "mine_five_bar":
        raise ValueError("Only the imported mapped closed-five-bar vehicle is supported")
    for key in ("leg_joint_names", "wheel_joint_names"):
        if list(cfg[key]) != MODEL[key]:
            raise ValueError(f"{key} differs from the imported vehicle metadata")
    for key in ("wheel_radius", "wheel_track_width"):
        if not math.isclose(float(cfg[key]), float(MODEL[key]), rel_tol=1e-7, abs_tol=1e-9):
            raise ValueError(f"{key} differs from the imported vehicle metadata")
    profile = cfg.get("hardware_profile")
    if profile != HARDWARE_PROFILE:
        raise ValueError(f"Checkpoint must use this vehicle's MCU hardware profile: {profile}")
    # 这里只有当前新车的下位机标定，不再回退到 CAD 导入时的旧力矩默认值。
    limits = {"leg_effort_limit": LEG_EFFORT_LIMIT, "wheel_effort_limit": WHEEL_EFFORT_LIMIT}
    for key in ("leg_effort_limit", "wheel_effort_limit"):
        if not math.isclose(float(cfg[key]), float(limits[key]), rel_tol=1e-7, abs_tol=1e-9):
            raise ValueError(f"{key} differs from the selected hardware profile")
    mapped = mapped_five_bar_geometry(cfg["five_bar_geometry"])
    for key in ("upper", "lower", "offsets"):
        if any(not math.isclose(a, b, rel_tol=1e-7, abs_tol=1e-9)
               for a, b in zip(mapped[key], MAPPED_FIVE_BAR[key])):
            raise ValueError("Checkpoint five-bar geometry differs from the imported vehicle")
    return mapped
```

函数首先检查车型，再检查关节名与顺序、轮半径和轮距。随后检查硬件参数版本、两类力矩上限和五连杆等效几何。

`math.isclose()` 用允许误差比较浮点数，避免 JSON 与 YAML 往返后很小的表示差异造成错误拒绝。它并没有允许明显不同的车型参数通过。

函数返回重新校验的等效几何。环境构造函数把返回值重新赋给 `cfg.five_bar_geometry`，再调用 Isaac Lab 基类初始化。

这属于“配置一致性检查”。它不会替你测量实物，也不是对每个 USD 刚体质量、惯量和接触参数的全面证明。

`Path(checkpoint).expanduser().resolve()` 先展开 `~` 并得到规范路径，随后用 `checkpoint.parent` 找权重所在目录。若目录下存在 `params`，就从那里读取 `env.yaml`；否则兼容配置直接放在权重旁边的组织形式。

`if not path.is_file(): raise ...` 使缺少配套配置成为明确错误。这很关键：两个策略都具有 27 维输入、6 维输出，仍可能使用不同关节顺序、轮径、动作尺度或质量模型，不能仅靠 `load_state_dict()` 的形状匹配来判断能否回放。

内部 `Loader` 继承 `yaml.SafeLoader`，再增加一个特定的元组标签构造器。其作用是兼容配置序列化留下的 `python/tuple`，不是允许任意 Python 对象从 YAML 执行。

`strip_retired_config_fields()` 处理已退出当前配置接口的历史字段。随后仍然调用 `validate_robot_contract(cfg)`，所以兼容旧字段名与放弃车型校验不是一回事。

返回的是读到的配置字典，不是已经加载到网络中的权重。入口还需要决定怎样把这些值还原到环境，并按显式实验覆盖构造运行配置；网络和优化器则由第四篇分析的 `runner.load()` 恢复。

```python
def strip_retired_config_fields(config):
    """Remove inactive saved fields without changing the checkpoint's env.yaml.

    Old sampling fractions are inactive only in grouped training or fixed-speed
    replay. Reject the retired random sampler instead of silently replacing it.
    """
    result = deepcopy(config)
    for key in RETIRED_CONFIG_FIELDS:
        group, field = key.split('.')
        if isinstance(result.get(group), dict):
            result[group].pop(field, None)
    commands = result.get('commands', {})
    if RETIRED_SAMPLING_FIELDS.intersection(commands):
        limits = commands.get('ranges_lin_vel_x', ())
        fixed_speed = len(limits) == 2 and limits[0] == limits[1]
        if not commands.get('grouped_training', False) and not fixed_speed:
            raise ValueError('Saved config uses the retired non-grouped random sampler')
        for field in RETIRED_SAMPLING_FIELDS:
            commands.pop(field, None)
    return result
```

这个调用也属于项目应用逻辑，先处理后续还要继续使用的配置副本。config 是从 env.yaml 读取的字典，result 是 deepcopy 得到的独立副本；整个函数不会回写检查点旁的 env.yaml。

第一个循环读取已退役字段集合中的 `group.field` 名称，拆出 group 和 field。只有对应 group 确实是字典时才移除字段，pop 的默认值 None 允许旧配置本来就没有该字段。这里清理的是已经没有运行意义的旧字段，不会把仍生效的控制参数整体删除。

第二部分检查命令字典里是否存在旧采样器字段。limits 是保存的线速度区间；两个端点相等才表示固定速度。若既没有 grouped_training，也不是固定速度，函数拒绝这份旧随机采样配置，避免把它静默解释成另一种训练任务。只有确认这些旧字段在当前组织形式下无效后，才逐项移除。

### 4.7 一个 USD 入口为什么能够组合很多文件

USD 的入口可以引用、叠加其他层。基础层保存原始导出几何和关节，后续层覆盖闭链、机械止挡、质量或碰撞形状。仿真最终看到的是这些层组合后的场景描述，而不是只读取入口文件中肉眼可见的几个属性。

因此，目录里多个 `.usd`、`.usda` 通常表示资产版本、组合层或不同用途的入口，不应按文件数量推断同时加载了多少台机器人。实际机器人数量由场景克隆配置决定。

同样，校准层把左轮质量改为 0.665 kg 后，不能再把原始 CAD 的旧质量汇总当成当前仿真的总质量。检查质量需要追最终组合结果；解释训练行为还要确认这次进程使用的是哪一个入口。

关节名、轮径等 JSON 数据与 USD 数据也可能分属两条路径：前者参与 Python 的索引和运动学计算，后者参与物理求解。两条路径需要一致，但不会因为改了其中一个文件而自动重写另一个文件。

### 5.2 重力前馈的质量定义

源码：[mcu_hardware.py](../../wheel_legged_gym_isaaclab/mcu_hardware.py)，第 46 至 53 行。

```python

GRAVITY_COMPENSATION_MASS_PER_LEG = NOMINAL_VEHICLE_MASS_KG / 2.0
GRAVITY_FORCE = GRAVITY * GRAVITY_COMPENSATION_MASS_PER_LEG

GRAVITY_ANGLE_BIAS = math.radians(2.0) + 1.57 - math.pi / 2
```

这段 `mcu_hardware.py` 记录的是所提供下位机固件的原始标定：整车 12.34 kg，每条腿基础支撑力为：

```text
F_base = 12.34 × 9.81 / 2 = 60.5277 N
```

2026-10-26 用户补充：机身还增加了 1.3 kg，其中 0.7 kg 为前电池，与原后电池对称，另外 0.6 kg 位于机身中部。因此，当前训练默认使用新的质量层：

```text
原整车质量 12.34 kg + 机身新增 1.30 kg = 当前名义整车质量 13.64 kg
原机身质量  8.47 kg + 机身新增 1.30 kg = 当前名义机身质量  9.77 kg
每条腿基础前馈 = 13.64 × 9.81 / 2 = 66.9042 N
```

当前质量由 [robot_model.py](../../wheel_legged_gym_isaaclab/robot_model.py) 读取 `manifest.json` 所选质量标定文件，再计算 `GRAVITY_FORCE`；`wheel_legged_vmc_flat_env_cfg.py` 从这里导入当前训练前馈。`mcu_hardware.py` 中的 12.34 kg 和 60.5277 N 仍表示原固件参考值，不会冒充更新后的实车参数。旧检查点仍按照自己的 `env.yaml` 恢复原资产和原前馈。

新质量层只修改机身质量属性，两侧整腿仍各 1.935 kg、车轮仍各 0.665 kg。由于没有单独的电池坐标和惯量测量，当前按用户确认的前后对称布置保留名义质心，机身惯量采用质量比例 `9.77 / 8.47` 的等效同形分布估计。这是待进一步校准的惯量估计，不能解释成从电池安装尺寸精确计算得到的结果。

质量改变后先冻结同一个策略，在相同命令、种子和重置扰动下比较旧、新质量的实际误差。改变质量不会让旧模型的验收结论自动适用于新模型物理条件。

这是两条腿的名义重力前馈基值，不是求解器强迫左右轮每一时刻承受完全相同的接触力。实际载荷还受运动、姿态、接触和机构惯性影响。

角度补偿怎样使用机身 pitch，将在第二篇结合函数调用分析。下位机协议和电机驱动细节只需在第四篇了解与框架输入输出一致性相关的部分。

## 六 观测缩放和观测裁剪要分开看

### 6.1 ObsScalesCfg 是数值缩放

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 31 至 41 行。

轮速 10 rad/s 乘 `dof_vel=0.05` 后变成 0.5。不同单位的物理量被调整到较接近的数值范围，有利于网络优化。

缩放不等于基于运行均值和方差的标准化。当前环境主动乘这些系数；ActorCritic 是否再启用经验归一化，要看它自己的配置和实际构造分支。

### 6.2 ObsClipCfg 是数值保护

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 44 至 60 行。

```python
@configclass
class ObsClipCfg:
    """Physical bounds applied before observation scaling.

    These limits are deliberately wider than the normal operating envelope.
    They are numerical guards, not task constraints.
    """

    lin_vel = 5.0  # [m/s]
    ang_vel = 20.0  # [rad/s]
    projected_gravity = 1.0
    theta = 3.1415926536  # [rad]
    theta_dot = 50.0  # [rad/s]
    leg_length = 0.5  # [m]
    leg_length_dot = 5.0  # [m/s]
    wheel_vel = 100.0  # [rad/s]
    action = 1.0
```

例如 `lin_vel=5.0` 表示观测块进入网络前被限制在 ±5 m/s，再乘缩放系数。它没有把训练速度命令范围改成 ±5 m/s，也没有给机器人施加一个速度约束力。

`action=1.0` 用于历史有效动作进入观测时的裁剪。某些已保存实验把轮动作执行上限设为 1.25，但这里仍将动作观测限制到 ±1。这两个字段控制不同环节，不能混为一个上限。

当前直接关节模式不把虚拟腿长作为 Actor 的单独观测块。配置中保留 `l0`、`l0_dot` 缩放项，是为了同一环境支持另一种执行分支，并不表示所有字段在当前分支都被读取。

### 6.3 缩放、物理量裁剪和最终观测裁剪的执行次序

以轮速观测为例，先从物理关节速度读取数值并按左右坐标转换，再进行物理范围保护，随后乘 `dof_vel`。最后拼成 27 维向量，还可能整体用 `clip_observations` 处理。每一步的输入与单位都不同。

教学例子：真实轮速为 12 rad/s，物理轮速保护为 ±100 rad/s，`dof_vel=0.05`。第一层保护没有改变 12，缩放后网络看到 0.6。如果误把 ±100 直接套到缩放后的数值，就已经换了保护对应的物理范围。

截断后的观测不再包含超出边界的精确幅度。若正常状态频繁碰到边界，Actor 会看到许多相同的极值，而实际速度继续变化。这时要先查单位、符号、异常物理状态与保护是否合理，不能仅靠增大奖励权重解决。

启用 ActorCritic 的经验归一化后，还会在网络入口按运行统计做另一层变换。物理缩放系数仍然存在；经验归一化并不会把环境中已经裁掉的信息恢复回来。恢复策略时，归一化统计若属于模型状态，也必须随检查点保持一致。

## 七 CommandsCfg 描述任务分布

### 7.1 命令不是动作

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 63 至 83 行。

```python

    heading_command = False

    heading_rate_limit = 0.5  # [rad/s], maximum corrective yaw rate

```

命令是任务目标，例如“以 0.4 m/s 前进、以 0.15 rad/s 左转、保持 0.30 m 高度”。动作是策略为实现任务而输出的六个执行参考。

代码里命令缓存有四列，但 Actor 接收前三列：前向速度、偏航角速度、机身高度。第四列用于可选航向目标，不等于第四个电机动作。

`resampling_time=5.0` 表示训练目标大约每 5 秒重新抽样一次，不表示策略每 5 秒才决策。Actor 仍然每 0.02 秒输出一次动作。

`linear_acceleration_limit=0.8` 限制命令的变化速度，而不是直接限制真实机器人加速度。每个控制步最多改变 `0.8×0.02=0.016 m/s` 的当前线速度命令。

### 7.2 为什么区分主速度区间和过渡区间

前进主区间是 0.2 至 0.8 m/s，倒车主区间是 −0.8 至 −0.2 m/s，过渡区间是 −0.2 至 0.2 m/s。

如果只练零速和较高速度，中间的小速度状态会覆盖不足。过渡区间专门补上从静止到运动的连接部分。

`speed_boundary_fraction=0.3` 使一部分样本恰好落在速度边界，避免连续均匀抽样时几乎从来不抽到最大速度本身。`yaw_boundary_fraction` 和高度边界抽样也有类似目的。

### 7.3 固定站立组和运动课程

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 84 至 104 行。


`fixed_standing_groups=True` 配合 `standing_env_fraction=0.25`，在速度训练阶段固定保留前 25% 环境训练零速站立。4096 个环境对应 1024 个固定站立环境；8192 个环境对应 2048 个。

这不等于当前所有环境都静止。是否全静止，还取决于 `training_motion_scale`、课程进度和最终命令抽样结果。

`training_motion_scale=0.0` 是源码默认值，表示把训练线速度和偏航目标缩到零。它不缩小高度范围，因此可以先训练“静止站立但高度改变”。成熟运动实验的保存配置使用 1.0，此时完整速度范围被放开。

`standing_only_steps`、`motion_ramp_steps` 和 `yaw_start_steps` 计的是控制步，不是 PPO 更新次数。默认 48000 控制步对应 960 秒仿真时间；在每次更新采集 48 步时，对应 1000 次更新的时钟长度。

这里说的是每个环境共享的课程时钟，不是把所有并行环境的步数再乘一次。8192 个环境并不会让 `common_step_counter` 每次增加 8192。

## 八 高度范围怎样从机械限位得到

### 8.1 进入 height_commands

源码：[height_commands.py](../../wheel_legged_gym_isaaclab/height_commands.py)，第 11 至 18 行。

```python
# Same asset chain as protected_stops_v2_live_cad/report.json. Conservative
# intersection of both legs and both overstroke tests, fixed root/zero gravity.
MEASURED_LEG_STOP_RANGE_M = (0.17886618077754973, 0.35423238188028333)
LEG_STOP_MARGIN_M = 0.01
# Rounded inward after applying the 10 mm margin, not firmware command extrema.
SAFE_LEG_LENGTH_RANGE_M = (0.19, 0.34)
UPRIGHT_HEIGHT_OFFSET_M = MODEL['wheel_radius'] - MODEL['hip_z']
SAFE_BASE_HEIGHT_RANGE_M = tuple(v + UPRIGHT_HEIGHT_OFFSET_M for v in SAFE_LEG_LENGTH_RANGE_M)
```

这里先保存限位测试得到的虚拟腿长范围，再留 10 mm 余量，并向内取整为 0.19 至 0.34 m。

`UPRIGHT_HEIGHT_OFFSET_M` 等于轮半径减去髋部几何偏置：

```text
0.06 − 0.02465354469 = 0.03534645531 m
```

因此直立时高度命令范围为：

```text
H_min = 0.19 + 0.03534645531 = 0.22534645531 m
H_max = 0.34 + 0.03534645531 = 0.37534645531 m
```

### 8.2 这个换算没有增加 IK 控制

`SAFE_BASE_HEIGHT_RANGE_M` 只决定高度命令抽样范围。Actor 看到高度目标后，仍然自己输出四个关节角目标。

代码没有在这个函数中求“这个高度对应哪个关节角”，也没有把命令腿长强制写入执行器。因此“利用几何选命令范围”与“利用 IK 执行高度目标”属于不同层次。

直立换算还包含姿态前提。机身倾斜时，实际世界高度并不总是简单等于虚拟腿长加这个常数。

### 8.3 命令范围不能代替完整机构约束

直接关节模式允许四个主动角分别变化，某些组合可能比安全命令对应的腿长更接近机械止挡。

所以要分别检查：目标角包络、CAD 止挡、闭链有效性、接触和实际腿长余量。仅看到命令范围留了 10 mm，不能据此认定四维动作空间中的每一个组合都留足 10 mm。

### 8.4 这里的高度是根部坐标，不是整车质心高度

奖励与回放主要使用 `root_pos_w[:,2]` 所代表的根部世界 z 坐标。这个点由资产的根刚体坐标约定决定，不随“给电池增加质量”就自动变成整车质心。

整车质心需要把各刚体的位置和质量加权求和；它可能随腿姿变化。轮心高度则与轮半径、地面和接触变形有关。三个高度有联系，却不是同一个观测量。

前面的 `H = L + wheel_radius - hip_z` 只用于直立几何下的命令范围换算。把机身 pitch 或腿摆角改变后，腿长的垂直投影会改变，不能把相同公式当作所有状态下的高度测量。

当前使用平地，地面参考 z 为固定值。若将来加入起伏地形，还要明确高度命令表示“世界 z”还是“相对脚下地面的离地高度”，并同步奖励、观测和验收定义；仅换 Terrain 配置不会自动重定义所有这些量。

## 九 RewardsCfg 怎样与算法配置分工

### 9.1 环境奖励的字段

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 108 至 135 行。

```python
class RewardsCfg:

    profile = 'joint_pd_balance_v1'
    tracking_lin_vel = 2.0
    tracking_lin_vel_enhance = 0.0
    # 窄核项目前关闭；速度误差以线速度跟踪和平方误差为主。
    tracking_lin_vel_precise = 0.0
    lin_vel_error_sq = -2.0
    lin_vel_error_lateral_multiplier = 1.0
    standing_velocity = 0.0
    base_height_error_sq = 0.0
    joint_target_leg_length_error_sq = 0.0  # opt-in FK decision cost; never changes joint targets
    tracking_ang_vel = 1.0
    yaw_rate_error_sq = -1.0
    spin_center_velocity = 0.0

    nominal_state = 0.0
    standing_leg_angle = 0.0

    dof_vel = 0.0

```

这些字段决定环境返回给算法的标量奖励。`tracking_lin_vel` 奖励线速度跟踪，`tracking_ang_vel` 奖励偏航速度跟踪，`orientation` 惩罚机身偏斜，`base_height` 奖励高度跟踪。

字段值为零，通常表示这一项不进入总奖励。它不一定意味着对应中间变量完全不计算；需要进入 `_get_rewards()` 才能确认。

`joint_target_leg_length_error_sq` 是一个可选的、通过正运动学评价关节目标的代价。即使启用，它也是训练评分，不会把 Actor 输出替换为 IK 结果。

### 9.2 sigma 和 clip 不是权重

`tracking_sigma_ang` 控制偏航指数奖励对误差的敏感程度，`tracking_ang_vel` 决定这一项的权重。`yaw_rate_penalty_clip` 则限制偏航负奖励幅值。

可以把三个作用分开：

```text
误差 → sigma 决定奖励曲线形状 → 权重决定幅度 → clip 决定上限
```

调整 sigma 不等同于增加所有情况下的惩罚。误差非常大时，窄指数核可能接近零；平方误差项是否存在、是否进入裁剪区，需要同时分析。第三篇的 PPO 只接收最后的总奖励，并不知道某个标量来自“高度”还是“偏航”。

### 9.3 PPO 的 loss 不写在 RewardsCfg

`entropy_coef`、`value_loss_coef`、`clip_param` 和 `learning_rate` 位于 `rsl_rl_ppo_cfg.py`。它们决定算法怎样使用数据更新网络。

例如 `orientation=-60` 是每步环境评分的一部分，`value_loss_coef=1` 是 Critic 损失权重。不能把它们直接放在同一张“奖励权重表”中比较。

### 9.4 对一个奖励字段，至少要沿三处代码读下去

第一处是配置，例如 `yaw_rate_error_sq = -1.0`。这只给出系数，尚未说明误差来自哪个坐标系、是否平方、是否裁剪。

第二处是 `_get_rewards()` 构造的信号。偏航项读取实际根部角速度与当前偏航命令，形成平方误差；高度项读取根部高度与当前高度命令。若命令本身正在斜坡变化，奖励比较的是当步命令，不能拿最终抽样目标直接代替。

第三处是各项加权、乘 `step_dt` 与总和裁剪的位置。例如一个未裁剪的平方误差系数从 −1 改为 −50，含义是同一误差对应的该项代价放大 50 倍；若该项早已被上限裁掉，继续增大系数可能只改变进入平台区的位置。

教学例子：偏航误差为 0.05 rad/s，平方为 0.0025。仅考虑未裁剪的平方项，系数 −1 时每控制步贡献为 `−1×0.0025×0.02 = −0.00005`；系数 −50 时为 `−0.0025`。总奖励还包含其他项，不能把这个数字直接解释成总损失变化或预计误差改善。

指数奖励中的分母也要按实际公式读。若写的是 `exp(-error_sq / sigma)`，分母 `sigma` 在量纲上对应误差平方，不能直接当作“允许误差为 sigma 米”。例如高度分母 0.0004 m²，对应的误差尺度是 `sqrt(0.0004)=0.02 m`。

### 9.5 零系数、奖励裁剪和验收门槛之间没有自动联动

把某项系数设为零，只控制它是否影响当前训练回报。它不会自动把相应验收要求从 `tracking_acceptance.json` 删除。反过来，调整验收门槛，也不会让 PPO 知道新的学习目标，除非训练代码明确读取并使用了那些字段。

`only_positive_rewards` 一类总奖励裁剪还可能把不同负回报都压到零：两个状态分别算出 −0.1 与 −0.5，裁剪后算法得到同一个数值。是否发生这种信息损失要用实际分项与裁剪前后数据核查，不能仅凭配置名字断言奖励设计有效或无效。

这也是第二篇保留原始分项、第四篇使用独立物理误差的原因。奖励用于学习；最终能否通过，应由冻结策略的实际高度、速度、姿态和持续运行数据回答。

## 十 环境总配置逐项解释

### 10.1 回合长度和空间维数

`episode_length_s=20.0` 表示正常时间上限约 20 秒。`decimation=4` 表示一个策略控制步推进四个物理子步。

`action_space=6`、`observation_space=27` 描述单个机器人的动作和观测维数。N 个并行环境形成 `[N,6]` 和 `[N,27]` 的张量，而不是一个具有 `N×27` 输入的巨大单体机器人。

`state_space=0` 表示没有单独声明额外状态空间。当前 Critic 使用的仍是名为 `policy` 的 27 维观测，不能解释为 Critic 没有输入。

### 10.2 关节名与刚体名不能混用

`leg_joint_names` 用于查找关节状态和写入电机参考；`leg_body_names` 用于查询腿部刚体的接触力。

`LB_joint` 是关节名称，`LB_link` 是刚体名称。两者即使名称相近，也位于不同索引空间。把 contact sensor 的 body ID 用到 `joint_pos` 上，结果没有物理意义。

`penalised_body_pattern` 是正则表达式，选择机身和腿部作为不希望持续触地的对象。正常车轮触地没有放入这组碰撞惩罚对象中。


这些字段描述“不安全状态持续多久才终止”。例如腿部接触力超过 5 N，还要持续满足相应计时条件才构成腿部触地失败。

这种计时可以容忍瞬时冲击，但不会让长期拖腿滑行算正常站立。`min_root_height=0.22` 是最低支撑高度保护，与高度命令误差的验收门槛不同。

`reset_velocity_initial` 和 `reset_velocity_final` 描述重置时根部线速度、角速度扰动的幅度。它们不设置稳态速度命令；改变这些参数会改变策略起步时需要恢复的初始状态分布。

### 10.4 `action_space` 是单机器人接口，GPU 张量才承载批量状态

`action_space = 6` 在基类中被转成单环境动作空间描述，说明每台机器人需要六个实数。场景环境数 `N` 则决定一次传入几行：`[N,6]`。

Actor 的第一层仍接受每行 27 个特征，同一组网络参数同时处理 N 行。把 4096 改成 8192，主要增加仿真状态、观测、动作和 rollout 缓冲数量；不会把网络第一层改为 `8192×27` 个输入。

空间描述也不能代替实际数值校验。一个张量形状正确，但含 NaN、左右轮符号错误或角度使用了度而非弧度，仍然可能使任务失败。空间解决“接口有几维”，控制契约解决“每一维究竟代表什么”。

### 10.5 失败保护与学习质量必须分开设置和解释

`max_body_pitch` 等字段控制何时结束一回合；验收中的机身姿态 P95 则评价策略是否足够稳定。策略在 20 秒内没有达到 30° 的终止角度，完全可能在大部分时间偏斜 5°，因此“没有倒”不能代替“站得稳”。

同理，`min_root_height` 是低支撑保护，不等于所有目标高度的允许误差。目标为 0.375 m、实际只有 0.29 m 时，根部仍可能高于 0.22 m 的保护值，但高度跟踪显然有问题。

重置扰动改变起步难度，失败持续计时改变回合终止条件，两者都应作为实验变量记录。不能为了让回放更好看而悄悄缩小扰动，随后与不同初态的旧结果直接比较。

### 11.2 闭链求解器参数

位置迭代数 128、速度迭代数 8 是 PhysX 约束求解器参数。闭链机器人需要同时满足关节与接触等约束，迭代不足可能影响约束误差和稳定性。

它们不是每步 Actor 推理次数，也不是 PPO 对一批数据学习的次数。把位置迭代数从 128 改为 256，不会让 Actor 每个物理步输出两次动作。

### 11.4 三组执行器

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 299 至 313 行。

```python
    actuators={
        "legs": ImplicitActuatorCfg(
            joint_names_expr=MODEL["leg_joint_names"],
            stiffness=leg_joint_stiffness, damping=leg_joint_damping, effort_limit_sim=LEG_EFFORT_LIMIT,
```

`legs` 匹配四个主动关节，设置位置驱动刚度和阻尼。`wheels` 刚度为零、阻尼非零，用于速度驱动。`passive` 的刚度、阻尼和主动输出上限为零，避免被动关节额外产生驱动力。

被动执行器的力矩上限为零，不表示对应刚体没有质量或不会受到关节约束力。它只是不作为主动电机输出通道。

顶层 `leg_effort_limit` 与嵌套执行器里的 `effort_limit_sim` 必须一致。环境 `_setup_scene()` 会调用 `synchronize_actuator_limits()`，在创建 Articulation 前同步这两处配置。

### 11.5 `prim_path` 里的表达式和磁盘路径不能互换

`/World/envs/env_.*/Robot` 中的 `.*` 用于匹配多个环境命名空间。真正的 USD Prim 例如 `/World/envs/env_0/Robot`，不会把星号当成机器人名字的一部分。

资产文件路径则是操作系统路径，例如 `.../mine_closed_chain....usda`。`UsdFileCfg` 把文件内容生成到场景中的指定位置；之后关节和接触传感器再按场景路径寻找物理对象。

这三层必须按顺序成立：磁盘文件存在；资产成功生成到预期 Prim；匹配表达式选到正确数量的实例。只验证文件存在，不能证明传感器的路径就匹配到了轮子或机身。

### 11.6 为什么执行器配置使用字典，以及匹配后还要查索引

`actuators` 外层字典中的 `legs`、`wheels`、`passive` 是执行器分组名称。组内 `joint_names_expr` 才选择真实关节；不能把字典键 `legs` 当作 USD 中的关节名。

列表形式的关节名同时表达目标集合和预期顺序。环境随后使用 `find_joints(..., preserve_order=True)` 得到实际 Articulation 索引。这个索引一般不是动作列 `(0,1,3,4)`，因此需要显式从六维动作中取出腿列，再写入真实关节 ID。

正则表达式形式的被动组可以一次匹配多根连杆关节，但仍应检查命中数量与模型版本。漏掉一个被动关节或与主动组重叠，都不能靠“字典里看起来有三组”来发现。

`effort_limit_sim` 送给隐式物理驱动，`leg_effort_limit` 还参与 Python 前馈限幅。两处设置意图不同：前者约束物理驱动输出，后者限制软件写入的显式参考。它们是否共同保证总执行力矩上限，需要结合求解器设置和实际测量，不能仅把两个配置值相同当作实证。

当前腿驱动为位置 PD：角度误差乘刚度，速度误差乘阻尼；轮驱动刚度为零，只保留速度误差通道。零刚度不表示轮子没有控制，零阻尼也不等于移除了碰撞与约束反力。

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 342 至 355 行。

### 12.3 接触传感器的历史、更新周期和查询维度

`history_length=3` 决定传感器内部保留多少帧接触历史。任务若读取当前 `net_forces_w`，就只在使用当前力缓存；必须显式读取历史字段，才是在计算最近三帧的统计。配置有历史不表示每一条失败判断都已经用了三帧均值。

`update_period=0.005` 表示期望的传感器更新间隔。场景在物理子步后更新资产和传感器，任务在控制步结尾读取它们。若将来只改 `sim.dt` 而不检查传感器周期，实际读取节奏可能与原设计不同。

接触力通常按 `[N,B,3]` 组织，三维是世界坐标力向量，`B` 是匹配到的刚体数。先对最后一维求范数，再对刚体轴做 `any` 或求和，分别得到“是否有接触”和“累计接触强度”。把这两个轴弄反会得到形状可能仍能广播、但含义错误的结果。

### 12.4 `replicate_physics`、克隆和环境隔离分别负责什么

场景复制使每个环境获得一台具有相同初始结构的机器人。`replicate_physics=True` 用于让框架复用同构物理结构的构建路径，减少大批量环境的建立成本；它不意味着每台机器人共享同一行动态状态。

`clone_in_fabric=False` 是本资产当前选择的克隆路径配置。不能仅从这一布尔值推导出“训练使用 CPU 物理”，实际仿真设备仍要看 `SimulationCfg.device` 和运行对象。

环境隔离还依赖碰撞过滤与场景命名空间。相邻机器人的几何可能处于同一个大世界中，所以环境原点间距、跨环境过滤和公共地面需要一起核查。间距大只是空间安排，不能替代过滤规则正确性。

地面材质示例中，若轮胎与地面均为 0.5、且实际组合使用 `multiply`，对应组合系数会是 0.25。这个算例说明需要检查双方材质与组合规则；当前某个资产的实际组合值，应读取其轮胎层再判断，不能套用算例。

## 十三 时间和求解器设置

### 13.1 一个动作持续多少时间

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 328 至 340 行。

```python
# -- simulation --
enable_external_forces_every_iteration: bool = True
sim: SimulationCfg = SimulationCfg(
    dt=1 / 200,
    render_interval=decimation,
    physics_material=sim_utils.RigidBodyMaterialCfg(
        friction_combine_mode="multiply",
        restitution_combine_mode="multiply",
        static_friction=0.5,
        dynamic_friction=0.5,
        restitution=0.0,
    ),
)
```

有三个节奏需要区分：

| 节奏 | 计算 | 当前值 |
| --- | --- | --- |
| 物理子步 | `sim.dt` | 0.005 s 即 200 Hz |
| 策略控制步 | `sim.dt × decimation` | 0.020 s 即 50 Hz |
| 一次 rollout | `48 × step_dt` | 每个环境 0.96 s |

Actor 每 20 ms 给一次动作，环境在随后四个 5 ms 子步重复应用参考。重力前馈读取物理状态，因此可以在子步内更新，而不需要 Actor 重新推理。

20 秒回合、0.96 秒 rollout 和 200 次 PPO 更新是三种长度。一次 rollout 可以包含某个环境的重置，也可以只是一个回合中的一段。

### 13.2 外力每次迭代开关怎样应用

源码位于 [physics_contract.py](../../wheel_legged_gym_isaaclab/physics_contract.py) 的 `apply_force_iteration_setting()`。环境 `_setup_scene()` 在物理开始前调用它，通过 USD 的 PhysX 场景属性写入并读回开关。

它影响 TGS 求解器内部处理外力的方式。它不把整车重力分给若干个时间段，不改变 9.81 m/s²，不提高 Actor 频率，也不把所写力矩乘上迭代数。

这是训练动力学的一部分，旧模型保存的缺省值与当前值不同就需要明确处理。`physics_contract.py` 的加载校验防止回放时无声切换。

### 13.3 post init 的 GPU 缓冲

源码：[wheel_legged_vmc_flat_env_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/wheel_legged_vmc_flat_env_cfg.py)，第 357 至 366 行。

```python
# -- sub-configs --
obs_scales: ObsScalesCfg = ObsScalesCfg()
obs_clip: ObsClipCfg = ObsClipCfg()
commands: CommandsCfg = CommandsCfg()
rewards: RewardsCfg = RewardsCfg()

def __post_init__(self):
    super().__post_init__()
    # 只增大详细闭链碰撞的 GPU 缓冲容量，不改变接触力或物理参数。
    self.sim.physx.gpu_max_rigid_patch_count = 2**20
```

`super().__post_init__()` 保留基类初始化逻辑。之后增大 GPU 接触 patch 缓冲容量，服务于详细闭链碰撞。

缓冲容量不是接触力大小。提高容量并不能自动修正错误质量或奖励；但容量不足可能导致仿真数据异常，因此属于运行可靠性配置。

### 13.4 `render_interval=decimation` 的赋值发生在配置构造阶段

这里的 `render_interval=decimation` 是在定义默认配置时用当时的值填入嵌套 `SimulationCfg`。它不是会自动跟随另一字段变化的公式对象。

例如后续只用 CLI 把 `decimation` 从 4 改为 2，不能未经检查就认为 `sim.render_interval` 必然也变成 2。若需要二者保持一致，应在实际覆盖完成后的配置中核对。这也适用于顶层 PD 参数与已经构造的执行器子配置。

渲染间隔决定什么时候需要更新可视图像，物理步长决定状态积分，策略间隔决定何时产生新动作。训练无界面时可能减少渲染开销，但不会因为不显示窗口而取消物理求解。

### 13.5 缓冲扩容与减少每步计算属于不同优化

`gpu_max_rigid_patch_count = 2**20` 表示为接触 patch 留足容量。这个整数不是要强制生成一百万个接触，也不是让每步计算一百万次碰撞。

容量不足可能导致警告或无效结果；容量充足后继续增大也不等于训练吞吐会提高。想提高效率，还要分别观测场景建立峰值、稳态主机内存、GPU 内存、仿真用时和 PPO 用时。

闭链模型的许多刚体、碰撞形状、USD 描述和 CPU 端物理元数据会消耗主机内存；策略张量和 GPU 求解缓冲会消耗显存。因此有剩余显存时仍可能受主机内存或场景构建限制，不能只看一张 GPU 利用率图作结论。


`gym.register()` 给任务 ID 关联环境类。`entry_point` 的字符串由“Python 模块路径”和“类名”组成，中间用冒号分隔。

`env_cfg_entry_point` 指向环境配置类，`rsl_rl_cfg_entry_point` 指向训练配置类。这两个键由后面的配置加载工具读取，不是 `gym.make()` 自动训练 PPO 的开关。

两个任务 ID 指向同一份环境和配置。真正选择直接关节还是显式 VMC，仍由 `leg_control_mode` 决定。

注册模块在导入时执行：

```text
train.py 导入 wheel_legged_gym_isaaclab.tasks
    → tasks 包导入 direct 子包
    → direct 子包导入轮腿任务模块
    → 任务 __init__.py 执行 gym.register()
    → 后面的 gym.make(task_id, cfg=env_cfg) 能找到类
```

新建环境时，如果只写了类却没有让注册模块被导入，任务 ID 仍然不存在。

## 十五 Hydra 和普通 CLI 如何共同修改配置

### 15.1 parse known args 的作用

训练入口使用 `parser.parse_known_args()`。已知的 `--num_envs` 等参数交给 argparse；剩余的 `env.rewards.base_height=3.0` 等表达式交给 Hydra。

`sys.argv=[sys.argv[0]]+hydra_args` 是重新组织 Hydra 能看到的命令行，而不是删除训练需要的普通参数；普通参数已经保存在 `args_cli` 中。

### 15.2 两份配置怎样进入 main

跨文件链路是：

```text
@hydra_task_config(task, agent_entry)
    → register_task_to_hydra()
    → load_cfg_from_registry(task, "env_cfg_entry_point")
    → load_cfg_from_registry(task, "rsl_rl_cfg_entry_point")
    → Hydra 应用 env.* / agent.* 覆盖
    → 配置对象 from_dict()
    → main(env_cfg, agent_cfg)
```

相关实现见 [hydra.py](../../../IsaacLab/source/isaaclab_tasks/isaaclab_tasks/utils/hydra.py) 和 [parse_cfg.py](../../../IsaacLab/source/isaaclab_tasks/isaaclab_tasks/utils/parse_cfg.py)。

`main()` 随后还会用普通 CLI 覆盖部分字段。例如 `--num_envs` 直接设置 `env_cfg.scene.num_envs`。如果同一字段在两种入口中都设置，必须按执行顺序判断最终值。

### 15.6 配置覆盖要按时间线判断，不能只看哪个文件更长

可以把普通入口概括为：类默认值 → 配置实例初始化及 `__post_init__` → Hydra 覆盖 → `main` 内普通 CLI 覆盖 → 环境构造中的同步和契约校验。实验专用入口若还恢复检查点配置、加载独立运行方案，则要把这些步骤插入它们实际执行的位置。

`from_dict()` 是更新字段的操作，不能假设每更新一个字段都会重跑整个 `__post_init__()`。因此修改顶层值后，已经构造的子配置可能需要入口显式同步；本项目在创建 Articulation 前同步执行器上限就是这种处理。

排查“我明明改了默认值，为什么训练没变”时，先看实际保存的 `params/env.yaml` 和进程启动参数，再查是否被检查点恢复或运行方案覆盖。直接继续修改多个文件，会失去判断哪一层真正生效的依据。

## 十六 从环境配置接到训练配置

源码：[rsl_rl_ppo_cfg.py](../../wheel_legged_gym_isaaclab/tasks/direct/wheel_legged_vmc_flat/agents/rsl_rl_ppo_cfg.py)，第 22 至 40 行。

```python
class WheelLeggedVMCFlatPPORunnerCfg(RslRlOnPolicyRunnerCfg):
    num_steps_per_env = 48  # 每个 env 采集 48 个控制步，再做一次 PPO 更新轮次。
    max_iterations = 1000  # 本次学习轮数默认值；CLI/恢复训练会另行解析。
    save_interval = 100  # runner 每隔多少 iteration 保存检查点，不是物理步数。
    experiment_name = "mine_wheel_legged_joint_pd_flat"
    # 键是 actor/critic 的输入角色，值是环境返回的观测组名；这里都读取同一帧 27 维。
    obs_groups = {"policy": ["policy"], "critic": ["policy"]}
    # wrapper 不提前裁剪，保证环境仍能看到 raw action 并计算饱和惩罚；
    # 最终执行前环境自己限制到 [-1, 1]，None 不代表电机无限幅。
    clip_actions = None
    policy = RslRlPpoActorCriticCfg(
        # 高斯策略新建时的逐维标准差，不是动作尺度；续训通常加载检查点中的 std。
        # actor 输出均值，训练从分布采样；act_inference() 回放直接用均值。
        init_noise_std=0.2,
        # 这里只给隐藏层尺寸；RSL-RL 从 obs/action 空间推导输入 27 和输出 6。
        actor_hidden_dims=[256, 128, 64],
        critic_hidden_dims=[256, 128, 64],
        activation="elu",
    )
```

`num_steps_per_env=48` 表示每次更新前，每个环境采集 48 个控制步。`obs_groups` 指定 Actor 和 Critic 都读取环境返回的 `policy` 组。

`clip_actions=None` 表示 wrapper 不预先裁剪动作。环境仍有执行限幅，且能看到原始 Gaussian 输出，用于计算饱和相关代价。

Actor 隐藏层 256、128、64 最终接到六个动作均值；Critic 相同隐藏层接到一个价值标量。这里并没有执行网络前向传播，只是在准备稍后传给 RSL-RL 的构造参数。

算法参数如何变成 `PPO` 对象、48 步数据如何变成 20 次 Adam 更新，将在 [第三篇](03_RSL_RL与PPO调用.md) 逐行分析。

### 16.1 `obs_groups` 两边的 `policy` 为什么不是同一个概念

字典键 `policy` 表示 Actor 输入角色，键 `critic` 表示 Critic 输入角色；列表中的字符串表示从环境返回数据里取哪个观测组。当前二者都取名为 `policy` 的 27 维组，所以输入数据相同，但网络参数仍各自独立。

若以后为 Critic 增加仿真中可读、部署时不可读的特权状态，可以新增一个环境观测组，再仅把 `critic` 角色指向它。不能只把 `state_space` 写成一个非零数字，就认为环境已经生成了对应状态、wrapper 已经传递、Critic 已经读到。

### 16.2 `init_noise_std` 只控制新建分布的初值

`init_noise_std=0.2` 表示从零创建策略时六个动作分布各自的标准差初值。加载检查点后，模型状态里的学习结果通常覆盖它；因此改这个默认值不等于已经给旧策略增加探索。

标准差在归一化动作单位中定义。腿角尺度为 0.3 rad 时，动作标准差 0.2 在尚未受执行限幅影响的范围内对应约 0.06 rad 的目标角扰动；轮速尺度 15 rad/s 下则约为 3 rad/s。相同动作标准差，并不表示相同物理强度。

`actor_hidden_dims` 只列隐藏层尺寸。网络最终的输入维数从观测组拼接结果得出，输出维数从动作空间得出。新任务若输入维数改变，必须同步处理旧权重兼容性；仅更改一份说明文档或输出头数量并不能完成迁移。

### 16.3 哪些配置属于一次更新，哪些属于整个运行

`num_steps_per_env=48` 控制每次采样长度；`num_learning_epochs=5` 与 `num_mini_batches=4` 控制同一批数据如何被重复学习，合计每轮 20 次 Adam 更新。它们都不修改 PhysX 的 128 次位置求解迭代。

`max_iterations` 由训练入口解释，恢复训练还要区分“本次追加多少轮”和“希望到达哪个累计计数”。`save_interval=100` 只决定定期保存的频率，不能用它证明每 100 轮都做了独立物理验收。

第四篇将把网络状态、优化器状态、课程进度和独立回放分别追踪。只有这些记录能对应起来，才能知道是在同一策略上继续优化，还是重新开始了另一个实验。

## 十七 自己搭建同类任务时应形成的文件关系

一个最小可训练框架至少需要以下职责完整连接：

```text
任务注册
    → 环境配置类
    → 环境类
        → 场景创建
        → 动作执行
        → 观测构造
        → 奖励
        → 失败和时间上限
        → 批量重置
    → PPO 配置类
    → 启动脚本
        → AppLauncher
        → gym.make
        → RslRlVecEnvWrapper
        → OnPolicyRunner
        → learn
```

从这里已经能看到：训练脚本不必重新实现 PhysX，环境也不必重新实现 PPO。真正要设计清楚的是各层之间的数据约定。

可以用三个问题检查自己是否理解本篇：为什么 `state_space=0` 时 Critic 仍有输入；为什么把环境数加倍不会把 Actor 输入维数加倍；为什么改高度命令范围不等于增加了 IK 控制。
