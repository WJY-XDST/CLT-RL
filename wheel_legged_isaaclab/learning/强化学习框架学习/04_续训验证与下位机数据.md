## 一 检查点不只是 Actor 权重

### 1.1 保存接口产生什么结果

接口源码：[on_policy_runner.py:289](../../../IsaacLab/_isaac_sim/kit/python/lib/python3.11/site-packages/rsl_rl/runners/on_policy_runner.py#L289)。

<!-- api-contract: OnPolicyRunner.save -->

| 项目 | 说明 |
| --- | --- |
| 作用 | 保存当前策略与继续训练需要的状态。 |
| 输入 | 目标路径 path，以及可选的附加元数据 infos。 |
| 输出 | None；写出检查点文件。 |
| 本步骤中的状态变化 | 当前普通 PPO 检查点包含 model_state_dict、optimizer_state_dict、iter、infos。 |

这些键是应用层恢复和审计所需的输出：model_state_dict 包含 Actor、Critic 与探索参数，optimizer_state_dict 包含 Adam 状态，iter 是库的迭代标签，infos 是调用方写入的附加信息。配套配置由应用层单独保存。

### 1.2 Adam 内部有什么

对每个有梯度的参数张量，Adam 通常保存：

| 内容 | 作用 |
| --- | --- |
| `step` | 已执行的优化器更新步数 |
| `exp_avg` | 梯度的一阶指数移动平均 |
| `exp_avg_sq` | 梯度平方的指数移动平均 |
| `param_groups` | 学习率、betas 等参数组配置 |

这些不是环境观测，也不是 reward 历史。它们影响下一次参数更新的方向和步幅。

只恢复网络而重建空 Adam，初始行为可以相同，但后续学习轨迹已不同。因此“加载了旧模型”与“完整恢复续训状态”不能互相替代。

### 1.3 当前十七组状态怎样核对

本工程恢复时核对八个 Actor 参数张量、八个 Critic 参数张量和一个 std，共十七组。这里关注它们是否被完整保存与恢复。

一次普通 PPO 更新包含 20 次 Adam 调用，所以在每个参数都持续参与训练的前提下，各组 step 应一致，并可用 `step/20` 核对实际更新次数。

如果某组 step 不一致，应先检查参数是否被冻过、某段损失是否没有梯度、是否更换过网络或优化器。不能直接选最大的一个 step 当作全部状态已完整恢复。

### 1.4 `state_dict()` 保存数值，不保存整个运行中的世界

`policy.state_dict()` 把模型的参数和已登记的持久 buffer 按名字组织起来。当前主要是 Actor、Critic、std；若启用带持久统计的归一化器，相应统计也应进入模型状态。

这个字典没有保存机器人此刻的世界位置、接触求解器缓存、所有 episode 长度、当前随机命令和半批 rollout。`torch.save()` 把字典序列化成文件，不会因为文件名叫 checkpoint 就自动捕获进程中的所有对象。

`infos` 是调用者传入的附加数据，默认可为空。只有项目确实向其中写入并在恢复时读取的内容才会产生作用，不能把它解释成 runner 自动收集的完整实验档案。

### 1.5 optimizer 的参数 ID 和模型参数名字怎样对应

模型字典按参数名组织，optimizer 状态则通过参数组与参数 ID 组织。加载时依赖新建网络的参数结构与顺序和保存时兼容，而不是自动从每个动量矩阵推断它属于哪个电机。

因此检查十七组状态，至少要核对对应参数、张量形状、step、`exp_avg`、`exp_avg_sq`，并检查各参数组 LR。只比较“字典长度都是 17”不足以证明恢复正确。

某个参数没有产生过梯度时，Adam 可能尚未为它建立状态；但成熟的当前普通 PPO 主线要求全部十七组已经存在并连续更新。遇到缺失应追原因，不能把它自动补零后仍声称无损恢复。

## 二 runner load 沿源码发生什么

### 2.1 加载接口恢复哪些状态

接口源码：[on_policy_runner.py:307](../../../IsaacLab/_isaac_sim/kit/python/lib/python3.11/site-packages/rsl_rl/runners/on_policy_runner.py#L307)。

<!-- api-contract: OnPolicyRunner.load -->

| 项目 | 说明 |
| --- | --- |
| 作用 | 把检查点中的已保存状态恢复到当前 runner。 |
| 输入 | path；load_optimizer=True 表示同时恢复优化器；map_location 指定设备映射。 |
| 输出 | 检查点 infos 元数据；模型、Adam 与迭代字段通过对象状态恢复。 |
| 本步骤中的状态变化 | 调用前必须先创建兼容网络；调用本身不重建机器人，也不自动恢复所有环境物理状态。 |

应用层下一步应核对完整模型、十七组 Adam、std 和实际 LR，再恢复课程；不是仅检查文件有没有读成功。

### 2.2 为什么必须先构造相同网络

加载权重前，runner 已经根据配置构造网络。若隐藏层尺寸或输入维数变了，state dict 形状可能无法匹配。

更隐蔽的是：形状完全相同，但观测语义变了。例如八维腿观测从虚拟腿状态换成主动关节状态，张量形状可以保持 27，而旧网络输入含义已不一致。

所以加载前还需要检查动作与观测约定，不能仅用“load 没报 shape error”证明模型兼容。

### 2.3 train 入口怎样调用 load

<a id="first-call-restore-adaptive-learning-rate"></a>

源码：[train.py](../../scripts/rsl_rl/train.py#L282)，第 282～290 行。

<!-- source-excerpt: wheel_legged_isaaclab/scripts/rsl_rl/train.py:282:290 -->

```python
if agent_cfg.resume:
    print(f"[INFO]: Loading model checkpoint from: {resume_path}")
    # load previously trained model
    runner.load(resume_path, load_optimizer=not args_cli.reset_optimizer)
    if args_cli.reset_optimizer:
        print("[INFO]: Loaded policy weights with a fresh optimizer state.")
    else:
        from wheel_legged_gym_isaaclab.training_state import restore_adaptive_learning_rate
        restored_lr = restore_adaptive_learning_rate(runner.alg)
```

`--reset_optimizer` 为假时加载完整 Adam，再进入学习率同步函数。当前持续优化走这条保留优化器的分支；这里暂停 train，带着 runner.alg 进入实现，不等到第四节才补原因。

#### 2.3.1 停在同步调用处，先分清两个学习率字段

PPO 构造时把配置学习率存入 `algorithm.learning_rate`，同时用它初始化 Adam 的 `param_groups[*]['lr']`。

加载 optimizer state 会恢复参数组 LR，但库的 `OnPolicyRunner.load()` 没有在那几行同步 PPO 自己的独立字段。

下一次 KL 自适应调节会读取 `algorithm.learning_rate`，再把结果写到 Adam。若这个字段仍是构造默认值，就可能覆盖刚刚恢复的实际 LR。

#### 2.3.2 调用学习率同步工具

<!-- application-recap: restore_adaptive_learning_rate -->

这个项目函数已在[第三篇 runner.load 后的首次调用处](03_RSL_RL与PPO调用.md#first-call-restore-adaptive-learning-rate-from-train)展开。它读取已恢复的各组 Adam lr，要求为正、有限且相同，再同步 PPO 的 algorithm.learning_rate，返回该 float。

这里复查三处去向：Adam 参数组保留加载值，PPO 调度字段取得同一值，调用方随后把 restored_lr 写回 agent_cfg.algorithm.learning_rate。它们的一致性是项目恢复逻辑的一部分。

#### 2.3.3 带着 restored_lr 回到训练入口

restored_lr 是工具返回的单一实际学习率。调用方随后把它写回 agent_cfg.algorithm.learning_rate 并打印；这一步让本次保存的配置与继续学习的状态一致。

源码：[train.py](../../scripts/rsl_rl/train.py#L291)，第 291～292 行。

<!-- source-excerpt: wheel_legged_isaaclab/scripts/rsl_rl/train.py:291:292 -->

```python
agent_cfg.algorithm.learning_rate = restored_lr
print(f"[INFO]: Restored PPO adaptive learning rate from optimizer: {restored_lr}")
```

至此，Adam 参数组、PPO 调度字段与待保存配置中的 LR 已明确对应。下一步继续核对课程和探索，而不是重新从配置默认值开始学习。

### 2.4 load 参数与返回值怎样使用

| 名称 | 在续训步骤中的用途 |
| --- | --- |
| path | 指向要恢复的检查点文件。 |
| load_optimizer | 决定是否恢复已保存的 Adam。 |
| map_location | 指定加载张量使用的设备。 |
| 返回 infos | 提供调用方保存的附加元数据，不是动作也不是新 runner。 |

load 的主要结果体现在原 runner 的状态中，因此后面的核对要读取 runner.alg.policy、optimizer 和计数等对象。

### 2.5 恢复完整学习状态与逐位复现未来轨迹有区别

保留网络、std、Adam、LR 和课程，是继续同一学习状态的必要条件。要让之后每个采样值和每一步轨迹都与中断前完全一致，还需恢复随机数生成器、环境物理状态、命令、历史、rollout 等更完整上下文。

原始 `save/load` 这段代码没有实现后一种完整进程快照。项目一般从声明的重置分布继续学习，再用匹配种子与配置做独立行为对比，因此不能把“全部十七组 Adam 恢复”说成“未来所有接触轨迹逐位相同”。

恢复瞬间可以单独验证：同一输入下推理相同；所有已保存模型张量相同；Adam 状态相同；两个 LR 持有位置一致。实际训练更新后再核对计数增加和参数发生有限变化，这比一句“load 成功”提供更多证据。

## 三 检查点配套配置为什么不可丢

### 3.1 一个可追溯实验目录

```text
某次 run/
├── model_7000.pt
├── model_7001.pt
└── params/
    ├── env.yaml
    ├── agent.yaml
    ├── control_contract.yaml
    ├── precision_mode.yaml
    └── curriculum_clock.yaml       有相应课程元数据时
```

`env.yaml` 解释动作映射、物理资产、驱动、命令与奖励。`agent.yaml` 解释网络和 PPO。`control_contract.yaml` 补充动作顺序、频率、力矩上限和硬件约定。

只把 `.pt` 文件拷到另一个目录而丢掉 `params`，会丢失判断兼容性和复现实验所需的信息。

### 3.2 加载配套车型配置

<!-- application-recap: validate_checkpoint_robot -->

其完整读取、兼容和车型校验流程已经在[第一篇配套配置读取处](01_环境构建与配置.md#first-call-validate-robot-contract-logic)展开。这是项目代码，不是 Isaac Lab 接口。

这里复用返回的配置字典作为 source_config，用于后续比较动作契约、资产、重置及物理设置。它只读取并校验配套配置；网络与 Adam 仍由 runner.load 恢复。

### 3.3 加载前还要验证哪些约定

<a id="first-call-resume-policy-contract"></a>
<a id="first-call-resume-physics-contract"></a>

这些项目函数已经移到[第三篇首次创建 wrapper 之前](03_RSL_RL与PPO调用.md#first-call-resume-policy-contract)，在真实调用处逐段展开。这里保留恢复结果的检查顺序：

| 检查 | 对应项目逻辑 | 通过后说明什么 |
| --- | --- | --- |
| 动作与观测契约 | `require_matching_policy_contract` | 控制模式、直接关节映射和维度等规定相容；仅 shape 相同不够。 |
| 重置 profile | `require_matching_reset_profile` | 默认相同；显式允许迁移时也只支持代码定义的方向。 |
| USD 资产选择 | `require_matching_robot_asset_setting` 与读取 helper | 路径相容或存在显式声明的物理变更；文件内容另需核对指纹。 |
| 外力迭代选项 | `require_matching_force_iteration_setting` 与读取 helper | 旧配置和本次设置一致，或显式声明物理变更。 |

它们校验配套配置，不加载网络、不执行 reset、不把属性写入 PhysX。实际加载模型与 Adam 仍通过后面的 `runner.load()`；底层库接口只需理解输入和恢复范围。

### 3.4 配置配对还必须包含 USD 的组合依赖

`env.yaml` 中的 `usd_path` 给出资产入口，但入口还可能通过 reference 或 sublayer 引用其他文件。若只复制入口文件，漏掉依赖层，重新打开时就可能丢失质量、轮胎碰撞或止挡覆盖。

可追溯的记录应明确实际入口及依赖层的内容指纹。哈希不同首先说明输入发生变化，不自动说明变化一定有害；哈希相同也只证明文件内容相同，不替代动力学验证。

模型分支应使用独立目录保存来源、覆盖配置、权重指纹和评估结果。两个文件都叫 `model_3200.pt`，可能来自完全不同的父检查点与修改方案，文件名不能作为唯一身份。

### 3.5 训练方案与源码默认值应同时记录

实验运行入口可以从历史 `env.yaml` 恢复配置，再有声明地覆盖一个全局奖励系数或探索下限。此时编辑器打开的默认类未必显示实际使用值，应读取本次运行的最终配置与生效记录。

这不意味着随意覆盖控制契约。改变动作顺序、单位或物理开关时需要识别它对旧权重的影响；一个单纯研究 yaw 奖励的试验，不应顺带改变重置角、轮径和低层驱动而不说明。

## 四 自适应学习率有两个保存位置

应用层调用与接口说明已经放到[续训入口第一次调用同步函数的位置](#first-call-restore-adaptive-learning-rate)。这里回看恢复后的对象对应关系：

| 保存位置 | 谁负责恢复或同步 | 后续谁读取 |
| --- | --- | --- |
| `optimizer.param_groups[*]['lr']` | `runner.load(..., load_optimizer=True)` | Adam 的参数更新 |
| `runner.alg.learning_rate` | `restore_adaptive_learning_rate(runner.alg)` | PPO 的 KL 自适应调度 |
| `agent_cfg.algorithm.learning_rate` | train 接收 helper 返回值后赋值 | 配置保存与后续实验记录 |

恢复检查应比较这三处数值，并同时核对完整 Adam。只看控制台打印的配置默认值，或者只看 optimizer 中的一处 LR，都不能证明下一次 KL 调整会从正确值出发。

## 五 文件名 课程时钟和实际更新次数

### 5.1 为什么 model 200 可能不是恰好二百次

原始 runner 使用从零开始的循环下标，并在更新后写 `current_learning_iteration=it`。第一次更新后标签可以是 0。

因此文件名 `model_200.pt` 不能脱离保存规则，直接解释成“恰好完成 200 次更新”。项目还需要用 Adam 和课程元数据核对。

#### 先读取并校验课程时钟

<a id="first-call-load-curriculum-clock"></a>

`load_curriculum_clock()` 和内部的 `make_curriculum_clock()` 已在[第三篇首次读取课程元数据](03_RSL_RL与PPO调用.md#first-call-load-curriculum-clock)处展开：从权重旁读取 `params/curriculum_clock.yaml`，并检查三个整数换算字段。没有配套时钟文件时返回 None，不假造一份时钟替代旧行为。

### 5.2 从完整 Adam 计算更新数

`clocked_update_count()` 的完整实现已在[第三篇首次使用 Adam 计数](03_RSL_RL与PPO调用.md#first-call-clocked-update-count)处解释。回到恢复核验，可以用下面三个量交叉比较：

| 量 | 本路线的例子 | 用途 |
| --- | --- | --- |
| 全部参数状态中的同一 Adam step | 84020 | 证明各参数完成的小批更新数一致。 |
| 每轮 Adam 小批数 | 5×4=20 | 将优化器 step 换算为 PPO 更新数。 |
| 实际完成更新数 | 84020÷20=4201 | 恢复课程和迭代计数，不从文件名猜测。 |

函数还要求 step 有限、为正、为整数并能整除每轮小批数；不一致或半轮状态会被拒绝。初始空 Adam 只有显式允许且 iter=0 才能按零更新处理，普通续训不能借此绕过缺失状态。

当前网络通常有十七份 Adam 状态，但这个函数本身没有验证状态数量一定为十七，也没有逐张量核对动量是否与源文件相同。因此计数通过之后，仍需要另外的完整状态核验。它只读检查点，不修改权重或优化器。

### 5.3 环境课程用的是控制步

课程时钟的基本关系是：

```text
common_step_counter = offset_steps + completed_updates × steps_per_update
```

当前每次 PPO 更新采集 48 个控制步，因此这里乘 48，不乘并行环境数量，也不乘 `decimation=4`。

`decimation` 用于物理步与控制步转换；Adam 次数 20 用于优化器步与 PPO 更新转换。这两个倍率不属于同一条时钟。

### 5.4 为什么要在 wrapper 首次 reset 前设置课程

wrapper 构造时主动 reset。若此时课程还是零，命令可能先按早期阶段抽样；稍后再改计数器，第一段交互分布已经不同。

训练入口因此先读取课程元数据、设置初始控制步，再创建 wrapper；加载检查点后继续校准 runner 的实际更新计数。

### 5.5 用实际更新数判断续训起点

调用方需要的结果是一个可信的 completed_updates。当前每轮 20 次 Adam，因此完整十七组状态若均为 64020，就对应实际 3201 次更新。若组间计数不一致或不在完整更新边界，工具拒绝给出可续训计数，应用层应先定位状态来源。

allow_initial 只服务于尚未学习的初始模型。后续每一块恢复的是选定的完整检查点，而不是再次套用初始模型例外。

### 5.6 四种计时在一块训练中分别增加多少

以 N=8192、每次 48 控制步、200 次更新为教学例子：每个环境增加 9600 个控制步，即 192 秒仿真时间；每个环境增加 38400 个物理子步；全批采样共 `8192×48×200=78643200` 条 transition；每组 Adam 增加 4000 次更新。

这些量都不是实际墙钟运行 192 秒。并行仿真与算法计算需要真实用时，其速度随硬件、模型复杂度和日志开销变化。

`episode_length_buf` 只计各自当前回合的控制步，失败重置后会清零；`common_step_counter` 服务于全局进度，不随单台机器人重置清零。把 episode 长度拿来当累计课程，会让反复失败的环境始终回到早期阶段。

## 六 探索参数的四种操作不能混淆

| 操作 | 改变什么 | 对续训的含义 |
| --- | --- | --- |
| 新策略 `init_noise_std` | 随机初始化 std | 只描述新建策略的起点 |
| 加载检查点 std | 恢复六个学习值 | 正常完整续训的一部分 |
| 显式 reset std | 将学习值改成指定数 | 属于额外实验变化 |
| 每步下限投影 | 阻止 std 小于声明下限 | 保留参数和 Adam，仍可训练 |

### 6.1 调用探索下限接口

<!-- application-recap: enforce_positive_exploration -->

该项目函数已在[第三篇首次安装探索保护处](03_RSL_RL与PPO调用.md#first-call-positive-exploration-from-train)展开，包括 std/log_std 的选择、六维下限、原地投影和更新后回调。

输入为策略、已有优化器、全局下限及可选轮下限；返回值是 PyTorch 的可移除 hook handle，由 exploration_guard 保存。实验配置另写日志文件。这里继续观察这种投影对恢复状态和后续探索的影响，而不再重复函数实现。

### 6.2 下限不等于把探索一直固定在该值

设下限 0.01 后，std 可以学到 0.02 或更大。只有它试图小于 0.01 时才被投影回去。

如果六个分量长期贴着下限，需要结合熵、动作均值变化、KL 和回放误差判断是否探索不足。不能仅因为设置了 entropy 系数，就假定探索一定充分。

### 6.3 腿和轮要换算成物理扰动

腿关节位置尺度是 0.3 rad，轮速尺度是 15 rad/s。std 都为 0.01 时，它们分别约对应 0.003 rad 与 0.15 rad/s 的参考扰动。

再由角扰动推断高度扰动，需要当前 Jacobian 和姿态。不能用某个姿态下的局部 0.44 mm 估算，概括整个高度范围和四维角动作组合。

### 6.4 在训练步骤中核对探索保护的结果

policy 是当前可学习策略，optimizer 是当前 Adam，minimum_std 与 minimum_wheel_std 是本次声明的下限。工具安装完成后，应用层应记录参数，并从保存模型读取六维实际 std，再结合动作尺度评估有效探索。

下限、当前数值和每次采样到的动作分别是约束、分布参数和随机样本。独立确定性回放使用均值，因此不能用一次带噪样本代替部署时行为。

### 6.5 提高探索、减少探索和恢复原值应按不同证据决策

当均值几乎不变、std 长期触底、有效动作范围又很窄时，提高探索可能帮助访问其他姿态；但仍要验证新采样是否主要被限幅挡掉，或显著增加跌倒。

如果带噪训练表现差、确定性回放却稳定，可能存在采样与部署行为差异；降低噪声可以作为全局对照试验，但不能凭一个例子推断它必然改善平均参考。

反过来，确定性 yaw 长期欠跟随而带噪 MAE 更大，也不能直接证明噪声就是欠跟随原因。要分别看 signed bias、波动、轮参考和执行响应，再决定是否调整 std、熵或奖励。

## 七 为什么按短训练块评估

### 7.1 一组二百次更新怎样组织

```text
选定已完成复验的检查点与配套配置
    → 当前资源与8192/4096容量检测
    → 校验普通PPO和完整状态恢复
    → 续训200次实际更新
        → 50/100等位置读取学习与采样诊断
    → 独立冻结回放
    → 对比稳定 高度 速度与偏航
    → 保留 修复或回退
    → 下一组
```

二百次是评估与决策的块长度，不是整个自主优化任务的终点。每块都可以从选定完整检查点继续，且保留被拒绝分支供分析。

### 7.2 回退是恢复哪一部分

恢复某个较早检查点，意味着 Actor、Critic、std、十七组 Adam 和实际 LR 一起恢复。不能只把 Actor 权重倒回去，再接上另一个分支的 Adam。

配置也必须说明是完全保留旧配方，还是做了一项新试验。对比试验最好只改变一个可解释因素，避免无法区分误差变化来自哪里。

### 7.3 容量测试为什么也要真实 PPO 更新

仅成功创建 8192 个机器人，不能证明 48 步 storage、反向传播和 Adam 的内存峰值都能承受。

容量检测因此使用完整配置、48 步采样和真实优化器更新，测试少量完整更新，再核对数值、资源与保存状态。测试权重留在独立目录，正式训练仍从选定原检查点开始。

这样测试的是“当前资源能否运行这一配方”，不是用容量测试结果代替行为验收。

### 7.4 短训块的结束是决策点，持续优化需要继续接上下一块

一块训练需要有限长度，才能固定候选策略、进行独立对照并决定下一步。200 次更新结束，不表示整个优化目标达成，也不能用“本块已结束”代替后续分析与继续推进。

复验通过且有可重复改善，就从该块完整状态继续；整体退步则保留该分支并回退；误差停滞则先查动作、执行、接触和学习信号，再设计一个有解释力的全局修改。这样持续的是诊断与优化闭环，而不是无差别堆训练轮数。

### 7.5 失败工况用于定位，训练规则仍需普适

按高度、正负速度和正负 yaw 分组统计，可以看出问题集中在哪些区域。这是评估和诊断，不要求在训练中写 `if height > ...` 给某一工况额外修正。

全局改变一个已有 yaw 平方误差系数，会对所有状态使用同一条公式；仅在失败高度或特定速度符号下添加奖励、动作偏置或固定命令表，则引入了工况条件化规则。后者容易把已知测点当成目标，环境复杂度变化后泛化风险更难解释。

本项目当前要求保留一般控制与连续命令采样。诊断可以精确到某一个失败 trial，但参数决策应验证全范围收益，并保护已通过工况的姿态与高度。

### 7.6 容量检查与正式模型的来源必须分开

真实五次容量更新会改变测试进程中的参数、std 与 Adam，所以容量模型应保存为独立证据。选择 8192 后，正式块仍从声明的父检查点完整加载，不能无记录地把容量测试的五次学习算进候选模型。

每个新块都需要重新确认资源与实际更新可用性。前一块跑过 8192，并不能保证当前应用占用、配置和资产变动后仍有足够启动余量；反过来，不能因为曾经失败就永久固定 4096。

## 八 独立回放与训练循环有什么区别

### 8.1 play 加载模型但不调用 learn

源码：[play.py](../../scripts/rsl_rl/play.py)，第 463 至 474 行。

```python
print(f"[INFO]: Loading model checkpoint from: {resume_path}")
# OnPolicyRunner 属于 RSL-RL，不是 LAB：此处借它构建 actor/critic 并加载权重。
# 不调用 runner.learn()，所以回放没有 PPO 参数更新。
if agent_cfg.class_name == "OnPolicyRunner":
    runner = OnPolicyRunner(env, agent_cfg.to_dict(), log_dir=None, device=agent_cfg.device)
else:
    raise ValueError(f"Unsupported runner class: {agent_cfg.class_name}")
runner.load(resume_path)

# get_inference_policy() 切到 eval 模式，返回 actor.act_inference 的可调用句柄。
# policy(obs) 得到动作均值 [N, 6]，不进行训练时的高斯采样。
policy = runner.get_inference_policy(device=env.unwrapped.device)
```

`get_inference_policy()` 切换评估模式，返回 `act_inference`。回放循环调用策略并推进环境，但没有调用 `PPO.update()`。

即使 `runner.load()` 的默认参数顺带恢复了 Adam，只要没有更新调用，权重也不会因此继续训练。

### 8.2 训练随机命令和固定验收命令

训练中的分组随机采样为学习提供覆盖。验收则显式固定速度、转向、高度、种子和持续时间，便于对比。

如果只在自己刚训练过的少数命令上测试，会漏掉其他高度和倒车转向组合。静止、原地旋转、直行中转向都需要独立覆盖。

### 8.3 确定性和带噪回放分别回答什么

确定性回放检查网络均值形成的闭环控制。带保存 std 的回放检查探索扰动下的行为和存活。

带噪结果好转不自动弥补确定性关键工况失败；确定性低误差也不能证明随机扰动下不会倒车失稳。两类数据都应保留，但按各自预先定义的标准解释。

### 8.4 独立回放的“冻结”具体冻结什么

冻结的是模型参数与更新过程：不调用 learn、backward 或 optimizer.step。环境仍然推进物理，策略每个控制步仍重新读取观测并输出动作，所以这是一套闭环控制，并非重播保存好的固定动作数组。

原始策略输出与诊断替代动作要区别记录。如果为了辨别轮驱动问题而手动替换轮参考，那是在测试执行环节，不能把它的好成绩记为原策略验收通过。

### 8.5 为什么快照要在自动 reset 之前取得

失败发生后，环境可能在同一次 step 内把机器人恢复到初始高度。若随后才读高度和姿态，日志会把真正的低支撑、碰撞或倒地状态替换成一个看起来正常的初始状态。

`evaluate_mine_policy.py` 的评估子类在 `_get_dones()` 中保存 post-physics、pre-reset 快照，并记录 episode ID 和失败原因。返回的下一帧 observation 可以已经属于新回合，但快照仍解释刚刚发生的旧回合反馈。

这条时序与训练 transition 的语义一致：旧动作产生旧回合 reward/done，下一观测可能是重置后的起点。独立评估应利用 episode 和 failure 标记保留这层关系。

## 九 误差从轨迹怎样计算

### 9.1 MAE 先逐点取绝对值

```text
error_t = actual_t − command_t
MAE = mean(abs(error_t))
```

先把正负误差平均再取绝对值，会让振荡误差相互抵消。例如 +0.05 和 −0.05 的平均偏差为零，但 MAE 仍为 0.05。

因此稳态偏差、振荡标准差和 MAE 应分别观察。相同 MAE 可能来自稳定偏置，也可能来自围绕目标快速摆动，修复方法并不一样。

### 9.2 非零命令的相对误差

```text
relative_percent = MAE / abs(nonzero_command) × 100
```

例如 yaw 命令 0.075 rad/s、MAE 为 0.015 rad/s，相对误差是 20%。不能用另一个更大的设计最大角速度作分母，再把它称为“该命令相对误差”。

零命令的百分比没有定义，应报告绝对漂移或按原验收绝对限值判定，不能把分母改成一、或者写零百分比。

### 9.3 原验收带绝对下限

原文件 [tracking_acceptance.json](../../../mine_model/config/tracking_acceptance.json) 规定相对误差 0.1，并为小速度、小偏航提供绝对下限。

| 项目 | 原配置中的关键值 |
| --- | --- |
| 相对误差 | 0.1 |
| 线速度绝对下限 | 0.025 m/s |
| 偏航速度绝对下限 | 0.025 rad/s |
| 轮速绝对下限 | 0.15 rad/s |
| 虚拟腿角设计范围 | 0.2 rad |
| 机身姿态 P95 | 2.5° |
| 最低支撑高度比例 | 0.9 |

小偏航命令可能满足原绝对下限，却仍超过命令自身的 10%。因此项目同时保留原七项判定和“所有非零命令严格小于 10%”报告；后者不删除前者的姿态、支撑高度与存活约束。

### 9.4 七项指标为什么不等价

速度和偏航比较机身运动与任务命令；高度比较根部高度与高度命令；腿长和腿角指标比较实际虚拟状态与相应参考；轮速比较实际轮速与轮参考；姿态指标限制机身倾斜。

轮速参考跟得准，不代表参考本身能产生正确 yaw。关节目标对应的腿长跟得准，也不代表倾斜机身的世界高度一定正确。

### 9.5 失败轨迹不能按低误差幸存部分汇总

若某个工况提前失败，仅统计失败前一小段稳定样本，可能得到很漂亮的 MAE。它仍然不是通过。

记录应保留提前失败、自动 reset、无定义指标和失败原因。不能把缺失值当零误差，也不能只展示幸存 trial 的平均数。

### 9.6 进入真正的七项计算函数，逐个读清聚合顺序

源码：[summarize_mine_trial.py](../../../mine_model/scripts/summarize_mine_trial.py#L46)，第 46～59 行。

<!-- source-excerpt: mine_model/scripts/summarize_mine_trial.py:46:59 -->

```python
def metrics_for_window(samples, case, criteria):
    """The same physical error definitions for ordinary and sustained gates."""
    return {
        'speed_mae_m_s': float(np.mean(abs(samples['speed_m_s']-samples['speed_cmd_m_s']))),
        'yaw_mae_rad_s': float(np.mean(abs(samples['yaw_rate_rad_s']-samples['yaw_cmd_rad_s']))),
        'height_mae_m': float(np.mean(abs(samples['height_m']-samples['height_cmd_m']))),
        'leg_length_mae_m': float(max(np.mean(abs(samples[f'{s}_length_m']-samples[f'{s}_length_ref_m'])) for s in ('left','right'))),
        'leg_angle_mae_rad': float(max(np.mean(abs(samples[f'{s}_angle_rad']-samples[f'{s}_angle_ref_rad'])) for s in ('left','right'))),
        'wheel_speed_mae_rad_s': float(max(np.mean(abs(samples[f'{s}_wheel_rad_s']-samples[f'{s}_wheel_ref_rad_s'])) for s in ('left','right'))),
        'body_p95_deg': float(np.percentile(np.maximum(abs(samples['pitch_rad']),abs(samples['roll_rad'])),95)*180/np.pi),
        'upright_support': bool(np.min(samples['height_m'])>=criteria['minimum_height_fraction']*case['height']),
        'command_reached': bool(np.max(abs(samples['speed_cmd_m_s']-case['speed']))<.005
                                and np.max(abs(samples['yaw_cmd_rad_s']-case['yaw']))<.005),
    }
```


前三项都先计算“实际量减当步命令”，逐点取绝对值，再沿窗口时间求平均。线速度和偏航不能只比较窗口平均实际量与窗口平均目标，那样会抵消正负振荡。

腿长、腿角和轮速先对左侧计算一个时间 MAE，再对右侧计算一个时间 MAE，最后取两者较大值。`max(mean(left), mean(right))` 与 `mean(max(left,right))` 不是同一种聚合，不能在复验中自行互换。

参考列也需要按记录来源解释。在当前直接关节模式中，虚拟腿参考通过实际执行的目标关节角做正运动学得到，用于检查参考实现；机身高度目标仍单独来自任务命令。参考腿长很准而任务高度很差，是可能发生的两层问题。

`body_p95_deg` 先对每个时刻取 `max(abs(pitch),abs(roll))`，再对这条序列求第 95 百分位，最后由弧度换成度。它不是 yaw 误差，不是 pitch 与 roll 的平方和，也不是轨迹最大倾角。

P95 可允许少量高于该值的瞬间，因此还需要失败保护和存活检查。不能因为 P95 低，就把某一次实际跌倒从结果里略去。

`upright_support` 用窗口内的最小根部高度，与 `minimum_height_fraction × case['height']` 比较。这里取的是 min，而不是均值；某一段明显下沉，不能由后面站高一点抵消。

`command_reached` 检查整段窗口里实际使用的速度与 yaw 命令，是否均已接近该 case 的最终要求。这可以排除速度斜坡尚未到达目标，就以较容易的小命令计算出漂亮 MAE 的情况。

### 9.7 原绝对下限通过，不等于非零命令严格小于 10%

原 yaw 限值为 `max(0.025, 0.1×abs(yaw_command))`。命令为 0.05 rad/s 时，限值是 0.025 rad/s；若 MAE 为 0.02，就通过这项原判定，但相对误差仍是 40%。

严格非零 10% 报告要求同一命令的 MAE 小于 0.005 rad/s。零命令则继续使用绝对漂移规则，不做除零。两个口径都保留，不能把原判定中的 `passed=True` 直接转述为“所有非零 yaw 误差小于 10%”。

轮速限值使用左右参考绝对值均值中较小的一侧，再与原绝对下限取较大者；腿角限值按设计范围比例计算，不是对接近零的每一帧腿角求百分比。每个指标分母必须追到源码，不能统一套用一个最大命令值。

### 9.8 “最坏误差”报告必须保留能找到原轨迹的信息

至少应报告检查点指纹、工况高度/速度/yaw、种子、时间窗口、MAE、相对误差和 signed mean。对全部 trial 求平均，可以说明总体；最坏 trial 则说明是否还有局部区域失败。

工况名只是标签，实际数值应从 manifest 的 case 记录读取。名为某个 canonical slot 的结果，也可能经过显式 command scale，不能靠名字猜最终目标。

若同一工况的三个种子只有一个失败，应保留这个失败并检查初态和扰动敏感性。把三个种子的 MAE 再平均成一个较小数，并不能代替逐种子通过要求。

## 十 为什么还要长时间和变命令复验

固定短工况只能证明该时间段的表现。长时间回放可以发现缓慢漂移、温和但持续的偏置和某个阶段才发生的状态积累。

高度阶跃检查动态升降，不等于三个固定高度均通过就自动通过；行进转向检查速度与偏航耦合，不等于原地旋转通过就足够。

当前审查覆盖固定工况、静止全高度、行进高度变化、前后退转向、正负速度的高度切换，以及小偏航持续回放。每一类回答不同问题。

对比应尽量使用同一命令序列、相同种子和相同初始网络观测。否则模型 A 较难、模型 B 较容易的初始状态，会掩盖实际差异。

### 10.1 持续窗口为什么要重叠

`assess_stability()` 先完成普通轨迹完整性和存活检查，再在声明的稳态区间中以 1 秒步距取 3 秒窗口。窗口重叠，可以减少“刚好把坏的一段切在两块边缘而稀释”的影响。

教学例子：总时长 120 秒，稳态从 17 秒开始，到 120 秒结束。3 秒窗口起点为 17、18、……、117，共 101 个。每个窗口都使用同一个 `metrics_for_window()`，没有换一套更宽的误差定义。

### 10.2 长时间结果如何聚合成一个 trial

对每项数值指标取所有窗口的最大值；对 `command_reached` 和 `upright_support` 则要求每个窗口都为真。随后用严格限值判断。

这个“最大值组合”中的最坏高度和最坏 yaw 可能来自不同窗口。报告适合说明该 trial 各维最差表现，但分析耦合原因时仍要回到对应时间段，不能假定所有最大误差都同时出现。

持续函数对时间差和每个窗口的样本数量也做检查，避免轨迹丢行后仍给出假通过。完整 120 秒存活是前置条件，不能只测试最后 3 秒看起来正常。

## 十一 高度不收敛时怎样沿代码查

### 11.1 先核对命令和实际高度的定义

从 `_commands[:,2]` 追到观测缩放，确认 Actor 真的收到目标。再确认 reward 使用的是 `root_pos_w[:,2]`，而不是把虚拟腿长误当世界根部高度。

机身几何偏置、轮半径和姿态都会影响高度关系。第一篇的直立换算只用于命令范围，不应拿来替代所有姿态下的实际高度测量。

### 11.2 再核对动作有没有能力改变高度

检查四个目标角是否随高度目标变化、是否卡在动作软饱和或关节角限位、实际关节是否跟随、力矩是否长期接近上限、闭链是否出现无效状态。

如果 Actor 输出变了但执行参考被裁剪成同一个角度，继续增加惩罚未必能解决可执行范围问题。

### 11.3 最后分析学习信号

查看实际高度误差分布对应的指数核值和平方代价，确认它们是否进入接近零或裁剪平坦区。再检查 std、熵、KL、实际 LR 和参数变化。

正奖励很小不等于全部学习信号消失；如果平方惩罚仍有效，仍有分数差异。但探索范围过小可能让策略很少访问更好的高度姿态。

这类分析应使用实际 rollout 和原始轨迹，不只根据配置表推断。

### 11.4 把高度偏差拆成“决策参考”和“参考实现”两段

可以先由执行的四个目标关节角计算目标末端几何，再与实际关节角计算的几何比较。这一步检查策略所要求的姿态与真实机构实现之间的差别。

若目标几何本身长期偏低，而实际基本跟随，重点查策略输入、奖励、探索和目标角包络；若目标几何合适、实际明显达不到，再查 PD、前馈、驱动力矩、质量与接触约束。

再从虚拟腿几何走向世界根部高度时，还要计算摆角、机身姿态和轮地接触的影响。不能只按一个固定 `dH/dq` 系数把所有高度误差归给关节误差。

改变质量分布会同时影响惯性、支撑偏差和所需力矩，旧策略在新模型下需要复验。名义总质量正确是一项校准，不是高度必然收敛的充分条件。

## 十二 偏航误差怎样拆成三个环节

### 12.1 先从轮速形成一个运动学参考

在前进为正的轮坐标下，理想无滑移的差速关系为：

```text
omega_ref_proxy   = radius × (wheel_ref_right − wheel_ref_left) / track
omega_wheel_proxy = radius × (wheel_actual_right − wheel_actual_left) / track
```

当前几何半径 0.06 m、轮距 0.4199 m。proxy 是理想运动学对照，实际轮胎接触和滑移可能使它与机身 yaw rate 不完全相同。

### 12.2 把总偏差写成可核对的和

```text
body_yaw − yaw_command
  = (ref_proxy − yaw_command)
  + (wheel_proxy − ref_proxy)
  + (body_yaw − wheel_proxy)
```

第一项检查策略给出的轮速差是否合适；第二项检查轮子对参考的跟随；第三项检查轮速与机身转向之间的接触运动差异。

如果误差主要在第一项，盲目提高轮速驱动阻尼可能解决不了 Actor 参考偏置。如果主要在第二项，应检查驱动、力矩限制和动力学；如果第三项明显，应检查接触、几何与滑移。

### 12.3 不同工况可能有不同主因

低高度高速倒车转向与高高度原地旋转，并不必然共享一个误差来源。应按速度符号、高度、转向符号和偏航幅度分别分析。

还要看 signed bias 与振荡。长期稳定少转，与持续左右抖动即使 MAE 相同，也不适合用完全相同的奖励或参数调整。

### 12.4 这三个分量是 signed bias 的代数分解，MAE 不能直接相加

逐时刻三个有符号分量相加，严格等于总偏差，取均值后仍满足同一加法关系。这适合检查一个稳定欠跟随主要出现在哪个环节。

但对各项先取绝对值再平均，三项 MAE 的和通常不等于机身 yaw MAE，因为不同分量可能相互抵消。可用三角不等式给上界，不能声称它是误差贡献百分比的精确分摊。

同样，`wheel_proxy − body_yaw` 只说明理想轮运动学与机身转动不一致。它本身不等于已经测出了滑移率，更不能单凭这一项断言轮胎摩擦一定有错。

### 12.5 轮速参考远低于限幅时，要避免把问题误归给最高转速

若欠跟随工况的两个轮参考只有零点几 rad/s，而目标包络为 15 rad/s，参考显然没有碰到这个速度限幅。此时提高最高允许参考未必改变该工况。

仍需检查低速速度驱动、静摩擦、接触约束、支撑姿态和策略给出的差速量。反之，高速组合若确实同时要求较大的前进与转向轮速，就要检查哪侧轮先触到限幅，以及实际力矩和跟随情况。

### 12.6 用失败区域诊断后，怎样做宏观改动对照

先固定父检查点、资产、初态和评估网格，比较原策略的好工况与坏工况。然后每次改变一个一般参数，例如已有 yaw 平方误差系数、轮驱动阻尼或探索约束，而不在控制代码中辨认并特殊处理失败标签。

候选策略不仅要使原坏工况改善，还要检查其他高度、正负速度和正负 yaw 有无明显退步。若只改善一个边界点却损害大部分原本通过区域，不能宣布这次修正有效。

## 十三 训练时序也需要核对

应该确认 Actor 看到的命令与 reward 使用的命令属于同一步，storage 保存的观测确实生成了该动作，old mean 和 old std 来自采样策略，而不是更新后的分布。

还要区分环境原始 reward 与超时价值补偿后的 storage reward。它们可以有声明过的差异，但不能出现无法解释的错位。

记录这些信息时应读取原始数据，不额外抽样动作或调用有副作用的观测函数。否则诊断本身可能改变 RNG 和命令历史，使待测训练不再是原训练。

### 13.1 只读审计要核对哪些相邻量

最基本的是 `obs_t`、采样动作、旧 mean/std/log probability、实际执行参考、reward 和 done 属于同一次交互。更新侧再核对新 log probability 的输入确实是同一条旧动作。

对于 raw action 与执行动作不相同的维度，要保留声明过的限幅映射；对于 timeout 奖励补偿，要保留环境原始 reward 与 storage reward 的区别。二者可以不同，但差值必须有源码依据。

### 13.2 诊断本身怎样避免影响待测对象

额外调用 `policy.act()` 会消耗采样 RNG，额外调用 `_get_observations()` 可能更新命令和历史，额外执行 `optimizer.step()` 则已经是在训练。诊断若使用这些操作，就不能继续自称纯只读。

可以在原调用已经生成数据的位置复制脱离梯度的记录，再由独立进程分析。即便如此，也应检查记录开销、写入完整性和 RNG 状态，避免将监测引入的变化误认为算法改善。

## 十四 下位机数据中必须对齐的部分

### 14.1 质量 质心和惯量影响物理响应

当前整车名义质量为实测 12.34 kg。每侧整腿 1.935 kg，包含 0.665 kg 车轮、不包含固定在机身上的髋电机。

按此质量划分：

```text
每侧腿部不含轮：1.935 − 0.665 = 1.270 kg
机身及固定部分：12.34 − 2×1.935 = 8.470 kg
```

单根碳纤维连杆的质量分配、质心和惯量仍依赖 CAD 体积估计；总称重准确，并不表示每根连杆都已单独实测。

两轮采用相同主惯量大小，并按镜像坐标处理惯量张量。惯量大小相同不要求不同局部坐标系中的所有交叉项符号也相同。

质量变化会改变位置驱动偏差、惯性和接触载荷，因此需要在新物理配置下重新验证，必要时续训。不能仅因为前馈名义质量已设置，就断言所有误差不受影响。

### 14.2 输出轴单位不能重复乘减速比

`mcu_hardware.py` 中腿和轮的力矩换算已经按照当前下位机输出轴约定组织。Isaac 关节坐标也描述输出轴。

因此不能再为了“换算到电机”无条件多乘一次减速比。应先确认接口数值究竟是电机侧电流、原始 CAN 命令，还是关节输出轴 N·m。

### 14.3 轮子 0.3 经验增益不是最终限幅

`WHEEL_UPSTREAM_TORQUE_GAIN=0.3` 对应原下位机 LQR 上游请求的经验缩放。它与最终 ±16000 CAN 命令裁剪不同。

当前仿真轮速隐式驱动没有直接套用这一上游增益。转成强化学习后是否需要类似环节，应依据整个执行带宽与接口标定，而不是把 0.3 机械地乘到所有轮动作或最大力矩上。

### 14.4 RPM 和左右轮符号

源码：[mcu_hardware.py](../../wheel_legged_gym_isaaclab/mcu_hardware.py)，第 77 至 79 行。

```python
def wheel_rpm_to_output_speed(rpm):
    """Firmware forward-positive output rad/s for raw [left, right] RPM."""
    return rpm * rpm.new_tensor([-1.0, 1.0]) * WHEEL_RPM_TO_OUTPUT_RAD_S
```

这是下位机原始左右 RPM 到前进为正输出角速度的换算。它的左右符号与仿真原始关节的转换边界不同，因为两者原始坐标来源不同。

用户提供 565 rpm 为额定转速，直接按输出轴 rpm 换算约为 59.17 rad/s；额定值不等于已经确认的绝对最高允许转速。

策略轮速参考 15 或 18.75 rad/s 是动作包络，PhysX 速度限制是另一个字段，硬件额定转速又是另一类数据。三个值应分别命名和保存。

### 14.5 重力前馈与控制频率

每腿基础前馈采用整车重力的一半，再按虚拟腿相对角、机身 pitch 和固定角偏置换算径向力。这个逻辑已在第二篇展开。

当前 Actor 50 Hz、物理与前馈更新 200 Hz；下位机代码中的 VMC 控制周期为 500 Hz。后续对齐实机时，应该明确谁更新策略、谁保持参考、谁计算低层 PD 和前馈，不能只复制网络权重而忽略时序。

### 14.6 质量准确度应分清实测总量和估计分布

整车 12.34 kg、每侧腿含轮 1.935 kg、轮子各 0.665 kg，是当前采用的称重约束。剩余腿部 1.270 kg 如何分配给各根碳纤维板和连接件，则依据 CAD 体积等信息估计。

仅知道材料是碳纤维板，还不能把全部连杆当作相同密度的实心外包盒。孔洞、板厚、叠层和金属连接件都会影响体积与质量；因此应记录估计方法和不确定性，而不是把推算值标成实测。

左右轮组件相同，主惯量大小应一致。若局部坐标轴镜像，惯量张量按坐标变换转换，交叉项可能变号；直接逐元素复制需要先确认两边轴约定相同。

### 14.7 额定转速不能与原始电机 RPM 混用

如果 565 rpm 确认是轮轴输出转速，则转换为 `565×2π/60≈59.17 rad/s`。固件函数却面对原始通信 RPM，并使用其既定换算系数与左右符号，二者输入层级不同。

不能把 59.17 rad/s 再套一次已经包含减速换算的系数，也不能从额定转速自动推导出最大安全速度。训练动作包络、仿真关节速度限制和实物额定值应分别保存。

### 14.8 弹簧前馈怎样在接口层理解

若气弹簧已经用腿长多项式建模，首先要明确多项式给的是虚拟径向力、实际弹簧轴向力，还是某个构件上的力。只有前者才能直接作为同一虚拟坐标中的径向广义力，借 `J^T` 映射到主动关节力矩；后者还需要安装几何的力臂或长度导数。

实物弹簧若已经提供支撑，电机补偿是加还是减，取决于希望施加的净支撑和模型符号。把弹簧的物理作用与同方向电机补偿重复加入，会改变策略所见动力学。

这类前馈仍与“另加一套按高度误差修正动作的 VMC 反馈”不同。后续需要统一求和、执行器上限和时序验证，本篇只解释接口原则，不表示当前训练已启用气弹簧模型。

| 想改变什么 | 首先查看 | 还要追到哪里 |
| --- | --- | --- |

| 关节角动作尺度 | `env_cfg.py` | `leg_control.py` 与部署动作约定 |

## 十六 从零搭建框架时的实际检查方法

先把动作、观测、单位和坐标写清，再用一个环境验证零动作和正负单轴动作。确认映射后，再检查小批量 reset、奖励与 done 的时序。

接上 wrapper 后，核对 TensorDict 中的键、形状和返回值个数。创建 runner 后，核对 Actor 输入输出和 Critic 输出，确认采样和确定性推理走不同函数。

完成一轮实际更新后，核对 storage 的时间和环境维、20 次 Adam 调用、checkpoint 中的网络与优化器状态。最后用新进程加载同一检查点回放，确认行为能复现。

这套顺序能把问题缩小到物理环境、接口适配、学习算法或恢复状态中的某一层。直接把环境数拉满、连续训练几千轮，再只观察总 reward，很难判断错误来自哪里。

## 十七 读完四篇后应能独立完成的练习

可以先选择一个参数，例如 `action_scale_vel`，从配置定义追到轮速目标，再追到物理驱动和回放轮速误差。随后换成 `tracking_sigma_ang`，追到指数奖励、总 reward、GAE 和策略损失。

这两个练习会形成两条不同的路径：前者直接改变执行参考的物理意义，后者改变训练评分而不直接改写当前动作。

再试着解释完整续训为什么需要同时保留网络、std、Adam、实际 LR、课程时钟与配套物理配置。如果能够在源码中逐项找到读取和写入位置，就已经建立了这个强化学习框架的主要结构。
